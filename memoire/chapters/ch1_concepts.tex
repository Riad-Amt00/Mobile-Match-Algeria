\chapter{State of the Art and Core Concepts}

This chapter establishes the technical and contextual foundation upon which the rest of the work rests. It first surveys the four disciplines this project draws on --- web data aggregation, web scraping, recommendation systems, and search engines --- then situates the work within the Algerian mobile telecommunications market and reviews the existing comparison platforms that have attempted to address consumer needs at the regional or international level. The chapter concludes by positioning \textit{Mobile Match Algeria} within the landscape identified through this review.

\section{Web Data Aggregation}

Web data aggregation is the systematic collection of information from multiple online sources to feed a single downstream application. The literature distinguishes three principal paradigms available to the practitioner:

\begin{enumerate}
  \item \textbf{Public APIs} --- the preferred path when a data owner exposes a stable, documented endpoint that returns the desired records. Integration is fast, the resulting feed is structured, and the rate limits are negotiated up front.
  \item \textbf{Syndication feeds (RSS, Atom)} --- cover a narrower set of use cases, typically blog posts or news articles, and are absent from most commercial domains today.
  \item \textbf{Web scraping} --- the fallback when the first two are unavailable: the aggregator visits the publicly-rendered pages and extracts the data from the HTML directly, with no cooperation required from the data owner.
\end{enumerate}

The choice between these paradigms has been examined empirically in the recent marketing-research literature. \textcite{BoegershausenDatta2022} review one decade of empirical work that collected web data and report that web scraping accounts for roughly 59\,\% of reviewed studies while API-based collection accounts for only 12\,\%; the authors attribute the gap to the simple fact that public APIs are rarely available for the specific records a researcher (or aggregator) needs, even when the same data is openly visible to any browser. \textcite{GlezPena2014} reach the same conclusion in a bioinformatics context with the influential survey \guillemotleft{}Web scraping technologies in an API world\guillemotright{}: web services are the de facto standard for biomedical data integration, yet scraping remains valuable for the wide range of data-integration scenarios that public Web services do not cover. The general lesson from both surveys is consistent: when a consumer-facing dataset is published as HTML but not as an API, scraping is the established and defensible method.

This lesson applies directly to the present project. The subject fiche allows two of these strategies --- \guillemotleft{}web scraping ou APIs\guillemotright{} --- but a thorough review of the public developer portals of the three Algerian operators confirms that the alternative does not exist in the consumer-plan domain. Each of the three operators exposes enterprise-oriented APIs --- documented endpoints for SIM-Swap detection, one-time-password verification under the CAMARA standard, direct carrier billing, and silent-number verification \parencite{GSMA2024}. These APIs target fraud-prevention, identity, and payment use cases. \textbf{None of the three operators publishes a consumer-facing API that returns the catalogue of mobile plans, their prices, or their data volumes}: the plan catalogue exists only as marketing content on each operator's website. The choice between the strategies listed in the subject fiche therefore resolves unambiguously in favour of scraping, in exactly the configuration the literature anticipates: an HTML-published consumer dataset with no API equivalent. The next section turns to how scraping is then realised concretely.

\section{Web Scraping}

Web scraping is the automated extraction of data from web pages. The technique has been the subject of dedicated academic surveys and is now an established research instrument in fields ranging from bioinformatics \parencite{GlezPena2014} to empirical marketing \parencite{BoegershausenDatta2022} and offer-catalogue aggregation \parencite{Mitchell2018}. The most recent systematic review of the field, by \textcite{KahlonSingh2026}, integrates 301 primary studies published between 2004 and 2025 across 198 peer-reviewed journal venues and 103 conferences; the authors map the evolution of scraping techniques, identify the dominant programming languages and tools, quantify performance metrics, and document the LLM-enhanced extraction approaches that have emerged since 2023. The reference architecture for a project of this type is in turn documented in the price-comparison literature: \textcite{ShaikhKhan2023} describe an e-commerce price-comparison website built on web scraping, in which a backend scraping pipeline aggregates product data from several retailers into a unified comparison interface --- the same architectural pattern that underpins the present project at the mobile-plan scale. The literature distinguishes two principal scraping approaches: a \emph{static} approach that retrieves the HTML through a plain HTTP request and parses it directly, and a \emph{dynamic} approach that loads the target page inside a real headless browser before reading the DOM. The two approaches differ on speed, resource cost, ability to handle JavaScript-rendered pages, and resistance to anti-bot defences; the choice between them therefore depends on the structure of the target sites rather than on aesthetic preference.

Reading the comparison column by column, dynamic scraping is the clearly appropriate choice for this project. Three rows of the table drive the decision. First, the row on \textbf{anti-bot defeat}: one of the three target operators deploys a protection layer that rejects plain HTTP requests outright, so static scraping fails on at least one of the three target sites regardless of any other consideration --- a single failure here is sufficient to disqualify the static approach for a uniform pipeline. Second, the row on \textbf{handling JavaScript-rendered pages}: even where the static approach works today, operators can shift to client-side rendering at any time without notice; a dynamic pipeline is robust to that change, a static pipeline is not. Third, the \textbf{resource cost} disadvantage of dynamic scraping (heavier memory and slower startup) is acceptable at the project's scale: scrapes run at most a handful of times per day, not in a tight loop, so the per-run cost is amortised over many hours of useful operation. The combination of these three rows --- one operator already blocks plain HTTP, the protection landscape can only get harder over time, and the cost disadvantage does not bite at this cadence --- makes the dynamic approach the proportionate engineering choice. The implementation details that follow describe how that choice was realised concretely.

Initial inspection of the three Algerian operator sites showed that plain HTTP requests were rejected or returned challenge pages on at least one of them, even though the underlying plan data is present in the initial HTML once the page is genuinely loaded in a browser. The dynamic approach was therefore retained for all three operators, providing a single uniform fetch path that is robust to current and future anti-bot deployments. The fetcher (\textit{src/lib/scraper/fetch.ts}) launches a real headless instance of \textbf{Microsoft Edge} via Playwright --- falling back to Playwright's bundled Chromium if Edge is unavailable --- with a French locale, the Africa/Algiers timezone, and a credible user-agent header. The returned HTML is then parsed with the lightweight \textit{Cheerio} library, which gives the project the robustness of a real browser fetch and the speed of server-side HTML parsing without paying for DOM traversal twice. Each URL is attempted up to three times, with spaced delays of zero, seven, and eighteen seconds, to ride out the intermittent connection resets of flaky operator servers; a per-operator circuit breaker switches to a verified fallback dataset after repeated failures.

Three plan families in the target catalogue could not be collected regardless of the parsing approach used. Three categories of obstacle were encountered: network-level refusal of automated connections; marketing pages with no machine-readable price structure; and image-only catalogues, where prices appear exclusively inside carousel image files (\textit{.jpg}) with no parseable text in the HTML. For these three families, a verified fallback dataset was manually constructed by visiting the operator websites in a standard browser in May~2026 and transcribing the values into the codebase. The specific families concerned and the operator each belongs to are documented in Chapter~3. The fallback data is served transparently and is visually distinguished from live-scraped data in the administrator dashboard.

\paragraph{Data normalisation and ethical considerations.}
Because each operator presents plan information in a different format, a normalisation pipeline is required to map raw scraped values to a common schema: unit conversion (MB to GB), removal of promotional suffixes from plan names, extraction of numeric values from strings containing units, and assignment of default values for fields not provided by a given operator. Ethically and legally, the project consumes only publicly visible marketing pages that no operator's \texttt{robots.txt} disallows, respects rate limits and inter-request delays, identifies its user-agent, and never collects any personally identifiable information; the data so collected is identical to what any visitor sees in their browser.

With a normalised catalogue being maintained automatically, the next question is how to surface relevant offers to individual users. The following section reviews the established paradigms for that task in the recommender-systems literature.

\section{Recommendation Systems}

\subsection{Classification of Recommendation Approaches}

Recommendation systems are a class of information-filtering tools that predict a user's preference for items based on available data \parencite{Geron2022, Raza2024Survey}. Closely-related projects in the same mobile / telecommunications domain have repeatedly applied recommender techniques to mobile-plan or mobile-device catalogues: \textcite{ZhangLiu2011TCPRS} present the Telecom Product Recommender System (TCPRS), a hybrid user-based / item-based recommender for mobile products and services that helps new customers select the most suitable plan; \textcite{SoftZulu2017Zambia} describe a recommender system deployed in the Zambian telecom market that uses call-detail records and demographic features to recommend products in a developing-country context comparable to the Algerian one; and \textcite{Chandrahaas2023Mobile} present a recent (2023) hybrid recommender for mobile phones that combines content-based filtering with collaborative filtering to handle exactly the same trade-off the present project faces. All three projects illustrate that the recommendation problem in this domain is real and tractable, and they confirm a difficulty the present project must navigate: at the start of a new aggregator's lifecycle, the user-interaction history the collaborative-filtering paradigm depends on is not yet available, forcing an alternative approach.

Recent systematic reviews confirm that this picture has not changed in 2024--2025. \textcite{PoniszewskaMaranda2025} review thirty-eight publications spanning 2013--2025 covering e-commerce recommender systems and find content-based filtering, collaborative filtering, and hybrid models still dominant; \textcite{Raza2024Survey} reach the same conclusion in a broader 2017--2024 review of the field. The choice of paradigm therefore turns on the data signal a project actually has --- exactly the dimension the literature uses to classify systems and exactly the dimension on which the present project must decide. The literature distinguishes three main paradigms whose characteristics are summarised in Table~\ref{tab:recsys-paradigms}.

The hybrid path remains available as a future evolution once interaction data accumulates --- a perspective acknowledged in the General Conclusion.

\subsection{Tiered Ranking with Explicit Priority Elicitation}

The plan-recommendation problem in this project differs from typical recommendation scenarios in that the item catalogue is small (fewer than 200 plans), fully enumerable, and characterised by well-defined numerical attributes (price, data, voice, SMS). This makes a content-based approach both appropriate and computationally efficient without requiring historical interaction data \parencite{Geron2022, LopsGemmisSemeraro2011}. The cold-start argument retained against collaborative filtering --- the absence of behavioural interaction history at a new aggregator's launch --- is taken from the recommender-systems literature \parencite{AdomaviciusTuzhilin2005} and has not been verified by an experimental collaborative-filtering prototype within the scope of this work.

A pure scoring model --- assigning each plan a single composite score and ranking by that score --- was prototyped at the design stage and proved unsatisfactory: weighted sums and weighted means both allowed unwanted compensation, in which a strong score on one dimension could mask a poor score on another, contradicting the user's stated priority. The model retained in this work therefore separates the problem into two layers. A first layer applies \emph{hard filters} (categorical constraints such as preferred operator, plan type, network generation, and the user-declared budget ceiling) that exclude incompatible offers outright. A second layer applies a \emph{tiered ranking}: the user's primary priority groups the surviving offers into broad tiers, and the user's secondary priority orders the offers within each tier. The composite key is constructed so that no within-tier improvement on the secondary priority can ever lift an offer past the boundary of a higher tier.

This design is an applied form of \textbf{lexicographic preference ordering with bounded relaxation} --- a multi-criteria decision-making technique established in the operations-research literature since the 1970s \parencite{Fishburn1974, Roberts1979} and characterised more recently in modern preference theory \parencite{GoswamiMitraSen2021}. Multi-criteria recommendation remains an active research area: \textcite{ParkYooShin2025} present at the ACM Web Conference 2025 a criteria-aware graph filtering approach that, like ours, treats the user's preferences as multiple separable dimensions rather than a single composite score, confirming that the multi-criteria framing is the current state of the art rather than a legacy choice. The cold-start framing --- recommending in the absence of historical interaction data --- is itself a well-studied subfield of recommender systems: e-commerce platforms face a continuous cold-start problem when their catalogue and customer base evolve faster than usage signals accumulate \parencite{BernardiKamps2016}, and the most recent comprehensive survey of the cold-start problem reviews 220 papers and confirms that content-based filtering with explicit user-declared preferences remains the dominant response when interaction signals are not yet available \parencite{ZhangColdStart2025}. The two layers of the present engine and the explicit two-slot priority elicitation are direct responses to that constraint at the project's scale. The full algorithm with its concrete formula, parameters, and iterative-design history is described in Chapter~3, Section~3.4. The contribution of this work lies not in the algorithm itself but in the adaptation: hard-filter / tiered-ranking split, explicit two-slot user-priority elicitation, and the integration with an automated scraping pipeline.

The recommendation engine answers \guillemotleft{}which plan suits my declared profile?\guillemotright{} A complementary query exists: \guillemotleft{}which plans match this free-text description?\guillemotright{}~--- the search problem, addressed in the next section.

\section{Search Engines}

A search engine is a software system that retrieves, from a body of content, the items most relevant to a user-supplied query. The information-retrieval literature distinguishes three broad families of search engine, each addressing a different content shape:

\begin{enumerate}
  \item \textbf{Web search engines} (Google, Bing) crawl the open Web and rank billions of unstructured pages against natural-language queries, relying on link analysis, behavioural signals, and recent large-language-model layers.
  \item \textbf{Enterprise full-text search engines} (Elasticsearch, Apache Solr, Meilisearch) index a defined corpus of documents and serve them through BM25-style ranking with facets, typo tolerance, and language-aware tokenisation.
  \item \textbf{Structured product search} retrieves items from a fixed catalogue of records whose attributes are known in advance (price, category, brand, specifications); the dominant retrieval mode here is the typed, attribute-driven query rather than the free-text query of the first two families.
\end{enumerate}

The present project belongs squarely to the third family. \textcite{ChenWANDS2022} present, at the European Conference on Information Retrieval, the WANDS benchmark for product-search relevance: 480 queries against a 43\,000-product Wayfair catalogue. Their results confirm that the dominant trade-off facing a search-feature designer is between \emph{relevance ranking} (which the user feels as result quality) and \emph{operational complexity} (which the engineer absorbs as build and maintenance cost). Two complementary academic perspectives further refine this trade-off. \textcite{Vandic2024Faceted}, in \textit{Data \& Knowledge Engineering}, develop a framework for approximate product search through faceted navigation combined with user-preference ranking: they show that for structured product offers --- exactly the shape of the present catalogue --- the natural retrieval model is a typed, attribute-driven query rather than a free-text full-text search, because the attributes themselves carry the bulk of the search semantics. \textcite{AliCaputo2023Facet} provide a comprehensive survey of facet-ranking approaches in faceted search systems and confirm that for catalogues whose items are described by a small, stable set of attributes, the appropriate retrieval model maps typed query tokens onto those attributes directly.

For very large free-text catalogues the relevance gain of an industrial BM25 engine clearly justifies its operational cost; at the opposite end of the scale, a small catalogue of a few hundred fully-structured items, the same trade-off can flip in favour of a far simpler approach. Three implementation options are commonly considered when adding a search feature to a structured product catalogue. Table~\ref{tab:search-families} summarises their characteristics.

Reading Table~\ref{tab:search-families} against the project's parameters --- a catalogue of fewer than two hundred plans whose attributes are already structured (price, data volume, network, type, operator) --- the trade-offs collapse to a clear conclusion. Vendor-published comparative analyses of the three families consistently report that industrial full-text engines such as Elasticsearch require a dedicated indexing service and substantial configuration before they reach Algolia-like instant-search latencies, that Meilisearch closes much of that gap at the cost of a separate process to operate, and that managed services such as Algolia charge a recurring per-request fee that is prohibitive for academic deployments \parencite{MeilisearchComparison2025}. No comparative benchmark of the three families was run on the project's own data: the catalogue size and the lack of free-text search queries make the experimental outcome predictable, and the operational-cost criterion alone separates the three families decisively. An industrial engine adds a second source of truth requiring synchronisation; a managed service adds a recurring fee incompatible with an academic budget; the hand-rolled structured-parser approach has no extra operational cost and maps the user's query directly onto the database columns the project already has. The hand-rolled approach was therefore retained: a small set of regular expressions extracts typed tokens (operator, data volume, price range, network, plan type, and feature keywords such as \guillemotleft{}unlimited\guillemotright{}) and translates them into a Prisma \texttt{where} clause. The same parser runs client-side to render the tokens as \guillemotleft{}Read as\guillemotright{} chips, giving the user an explainable view of how each query was interpreted --- a transparency property that opaque industrial engines do not offer out of the box.

With the four technical disciplines mapped --- aggregation, scraping, recommendation, and search --- the chapter now turns to the specific market in which they are applied: the Algerian mobile telecommunications sector.

\section{The Algerian Mobile Telecommunications Market}

\subsection{Market Overview and Key Figures}

Algeria's mobile telecommunications sector is regulated by the Autorité de Régulation de la Poste et des Communications Électroniques (ARPCE). According to ARPCE's most recent quarterly observatory, the country counts more than 54~million mobile subscribers in the first quarter of 2025 --- a 4.4\,\% increase over the same quarter of the previous year --- distributed across three licensed operators: Mobilis, owned by the state-controlled Algérie Télécom group; Djezzy, majority-owned by VEON; and Ooredoo, a subsidiary of the Qatari group Ooredoo \parencite{ARPCE2025, ARPCE2024, Statista2024}. Mobile penetration stands at approximately 106\,\%, reflecting a mature market where many users hold multiple SIM cards.

The network infrastructure has evolved considerably over the past decade. Following the deployment of 4G LTE services in 2016, all three operators have expanded coverage progressively across the country. Djezzy launched commercially limited 5G trials in 2024, positioning itself as the first operator to test fifth-generation technology in Algeria \parencite{GSMA2024}. These developments have accelerated the diversification of plan offerings, as operators compete on price, data volume, and network quality.

\subsection{Offer Complexity and the Consumer Decision Problem}

Each operator publishes a catalogue of prepaid, postpaid, and data-only plans that is updated several times per year. Prices range from a few hundred to several thousand Algerian Dinars per month, depending on the included data volume (from 1~GB to over 200~GB), voice minutes (from limited bundles to unlimited calls), SMS allowances, and validity periods (daily, weekly, monthly, or longer). A consumer wishing to identify the most cost-effective plan for their specific usage profile must visit three separate websites, compare offerings across heterogeneous formats, and account for promotional periods that may alter the base price.

\section{Existing Comparison Platforms}

Several international platforms have successfully addressed the plan-comparison problem in their respective markets, and one Algerian multi-vertical comparator addresses part of the same need locally. This section reviews both and then positions \textit{Mobile Match Algeria} against them.

\paragraph{International benchmarks.}
An analysis of three established international platforms reveals common features, architectural patterns, and limitations that inform the design of the present work.

\textbf{MonPetitForfait} (France, founded 2013) is an independent French aggregator that covers all four national operators (Orange, Bouygues Télécom, SFR, Free Mobile) plus a wide set of virtual operators (RED by SFR, B\&YOU, Sosh, Prixtel, and others). It provides a tabular comparison interface, a plan-finder questionnaire, and user reviews. The platform relies primarily on operator partnerships and manual data entry rather than automated scraping, which limits how quickly its catalogue reflects operator-side changes. It does not offer a personalisation engine beyond basic filtering \parencite{MonPetitForfait2026}.

\textbf{WhistleOut} (Australia and the United Kingdom) operates a comparison marketplace that includes both mobile plans and broadband. It features a strong search and filter interface and integrates affiliate referral links. Its data is updated through a combination of operator feeds and editorial review. The platform targets English-speaking markets and its architecture is not publicly documented.

\textbf{CompareTheMobile} (United Kingdom) offers a highly visual comparison interface with side-by-side plan cards and a compatibility checker for handsets. Like its counterparts, it depends on voluntary operator data submission and does not employ automated collection.

\paragraph{An Algerian comparator: Comparili.net.}
One local platform was identified that addresses part of the same need. \textbf{Comparili.net}, founded in 2020 by three Algerian entrepreneurs, is a multi-vertical comparator that covers business software (CRM, ERP, accounting), web hosting and online services, banking cards, and mobile telephony in a single WordPress-based site \parencite{Comparili2024}. Mobile plans appear as one of several categories alongside the software and hosting verticals that dominate the platform's positioning (\guillemotleft{}le comparateur N\textsuperscript{o}1 des logiciels métiers informatiques\guillemotright{} according to its own home page). Its mobile-plan section provides a filter-based comparison of SIM-card offerings supported by editorial articles and user reviews \parencite{Comparili2024}.

The existence of Comparili.net confirms that a market demand for comparison tools in Algeria is real and already partially served. It also delimits a clear positioning space for the present work. Mobile Match Algeria differs from Comparili.net along five axes:

\begin{itemize}
  \item \textbf{Scope}: Comparili.net is a multi-vertical comparator with mobile plans as one section among many; Mobile Match Algeria is a dedicated mobile-plan platform with a deeper feature set on that single vertical.
  \item \textbf{Data acquisition}: Comparili.net is editorially curated and enriched by user-submitted reviews; Mobile Match Algeria relies on an automated scraping pipeline that synchronises offers from the three operator websites on a scheduled basis.
  \item \textbf{Personalisation}: Comparili.net offers filtering and a SIM comparison page; Mobile Match Algeria adds a tiered-ranking recommendation engine that orders offers by the user's declared budget, usage profile, and priority ranking.
  \item \textbf{Language}: Comparili.net is published in French; Mobile Match Algeria offers a trilingual interface (French, English, Arabic) to extend reach within the Algerian user base.
  \item \textbf{Openness}: Comparili.net is a proprietary WordPress platform; Mobile Match Algeria is open-source and intended as both a consumer tool and an academic artefact.
\end{itemize}

\paragraph{Gap analysis for Algeria.}
Beyond Comparili.net, none of the international platforms identified above serve the Algerian market directly. The absence of additional comparators can be explained by several structural factors: the relatively small number of operators (three), the absence of virtual operators, and the lack of public APIs that would facilitate data integration. The international platforms reviewed rely on operator cooperation or affiliate relationships that do not exist in the Algerian context. Furthermore, none of these platforms --- Comparili.net included --- offers an Arabic-language interface, which is essential for reaching the full Algerian user base, nor a deep multi-criteria scoring recommendation engine tailored to mobile-plan attributes.

\section{Positioning of This Work}

The preceding review establishes that the only Algerian platform addressing this need --- Comparili.net --- covers mobile plans as one vertical among several and relies on editorial curation and user reviews rather than on automated aggregation. No \emph{dedicated} mobile-plan platform with deep multi-criteria features for Algerian consumers currently exists. The combination of scheduled automated data collection, a tiered-ranking recommendation engine with explicit priority elicitation, a structured search interface, a savings calculator, a notification system, a multi-language interface (English, French, Arabic), and a side-by-side comparison view distinguishes \textit{Mobile Match Algeria} from both the international platforms reviewed and from the local Comparili.net offering.

The application is built on a contemporary full-stack JavaScript stack centred on three pillars: \textit{Next.js 16} as a React-based framework supporting server-side rendering, the file-system-based App Router, and back-end API routes inside the same project \parencite{NextJSDocs2024}; \textit{Prisma 7} as a type-safe database toolkit whose single \textit{schema.prisma} file is the unique source of truth for the data model and from which TypeScript types are auto-generated \parencite{PrismaDocs2024}; and \textit{SQLite} as a serverless, file-based relational database that provides adequate performance and zero operational overhead at the project's scale. The full justification of these choices, together with the rejected alternatives (Nuxt, SvelteKit, TypeORM, Drizzle, PostgreSQL, MySQL), is developed in Chapter~2 Section~2.8. The following chapter translates the requirements identified in this review into a concrete system design.
