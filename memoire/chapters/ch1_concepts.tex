\chapter{State of the Art and Core Concepts}

This chapter establishes the technical and contextual foundation upon which the rest of the work rests. It first surveys, as pure research, the disciplines and design concerns that underpin an automated mobile plan comparison platform, web data aggregation, web scraping, recommendation systems, and search engines, then the comparison and visualization of results, notification systems, and responsive accessible delivery, reviewing for each the underlying concepts and the tools the literature offers, without reference to this project. It then situates those techniques within the Algerian mobile telecommunications market and reviews the existing comparison platforms. Only in the concluding section does the chapter return to the project, to state, for each, which tool or technique was chosen after this research and why.

\section{Web Data Aggregation}

Web data aggregation is the systematic collection of information from multiple online sources to feed a single downstream application. The literature distinguishes three principal paradigms available to the practitioner:

\begin{enumerate}
  \item \textbf{Public APIs}, the preferred path when a data owner exposes a stable, documented endpoint that returns the desired records. Integration is fast, the resulting feed is structured, and the rate limits are negotiated up front.
  \item \textbf{Syndication feeds (RSS, Atom)}, cover a narrower set of use cases, typically blog posts or news articles, and are absent from most commercial domains today.
  \item \textbf{Web scraping}, the fallback when the first two are unavailable: the aggregator visits the publicly rendered pages and extracts the data from the HTML directly, with no cooperation required from the data owner.
\end{enumerate}

The choice between these paradigms has been examined empirically in the recent marketing research literature. \textcite{BoegershausenDatta2022} review one decade of empirical work that collected web data and report that web scraping accounts for roughly 59\,\% of reviewed studies while API based collection accounts for only 12\,\%; the authors attribute the gap to the simple fact that public APIs are rarely available for the specific records a researcher (or aggregator) needs, even when the same data is openly visible to any browser. \textcite{GlezPena2014} reach the same conclusion in a bioinformatics context with the influential survey \guillemotleft{}Web scraping technologies in an API world\guillemotright{}: web services are the de facto standard for biomedical data integration, yet scraping remains valuable for the wide range of data integration scenarios that public Web services do not cover. The general lesson from both surveys is consistent: when a consumer facing dataset is published as HTML but not as an API, scraping is the established and defensible method. Having established that scraping is the appropriate aggregation method whenever a consumer facing dataset is published as HTML without an equivalent API, the next section examines how scraping is realised in practice.

\section{Web Scraping}

Web scraping is the automated extraction of data from web pages. The technique has been the subject of dedicated academic surveys and is now an established research instrument in fields ranging from bioinformatics \parencite{GlezPena2014} to empirical marketing \parencite{BoegershausenDatta2022} and offer catalogue aggregation \parencite{Mitchell2018}. The most recent systematic review of the field, by \textcite{KahlonSingh2026}, integrates 301 primary studies published between 2004 and 2025 across 198 peer reviewed journal venues and 103 conferences; the authors map the evolution of scraping techniques, identify the dominant programming languages and tools, quantify performance metrics, and document the LLM enhanced extraction approaches that have emerged since 2023. The reference architecture for a system of this type is in turn documented in the price comparison literature: \textcite{ShaikhKhan2023} describe an e commerce price comparison website built on web scraping, in which a backend scraping pipeline aggregates product data from several retailers into a unified comparison interface. The literature distinguishes two principal scraping approaches: a \emph{static} approach that retrieves the HTML through a plain HTTP request and parses it directly, and a \emph{dynamic} approach that loads the target page inside a real headless browser before reading the DOM. The two approaches differ on speed, resource cost, ability to handle JavaScript rendered pages, and resistance to anti bot defences; the choice between them therefore depends on the structure of the target sites rather than on aesthetic preference.

Reading the comparison, the decisive factors are anti bot resistance and the handling of JavaScript rendered pages. Whenever a target site rejects plain HTTP requests or builds its content client side, the static approach fails and the dynamic approach becomes necessary; and because such protections tend only to spread over time, a dynamic pipeline is also the more future proof option. Its principal drawback, heavier memory use and slower startup, is immaterial for catalogues that are refreshed periodically rather than scraped in a tight loop. The range of tooling that realises a dynamic pipeline is surveyed next.

\subsection{Tool Landscape}

A range of tools realises these two approaches across language ecosystems. Static parsing is served by HTML libraries such as Cheerio (Node.js) and BeautifulSoup (Python), and by full crawling frameworks such as Scrapy (Python). Dynamic scraping is served by browser automation libraries, among them Playwright, Puppeteer, and Selenium, which drive a real headless browser through its full client side runtime. Two further categories address content that is published only as images rather than as machine readable HTML: managed page to data services such as Firecrawl, and artificial intelligence extractors, namely optical character recognition (OCR) engines such as Tesseract and vision language model APIs. \textcite{GlezPena2014}, reviewing the same landscape across language ecosystems, reach a conclusion that recurs throughout the literature: there is no universal best tool, only a best tool given the structure of the target sites, the language stack already in use, and the operational budget available.

\paragraph{Data normalisation and ethics.}
Two concerns are common to any scraping effort, independent of the tools chosen. The first is \emph{normalisation}: because each source presents its data in a different format, a pipeline must map raw values to a common schema through unit conversion, removal of promotional text, extraction of numeric values from labelled strings, and assignment of defaults for fields a given source does not provide. The second is \emph{ethics and legality}: the established practice is to consume only publicly visible pages that a site's robots.txt does not disallow, to respect rate limits and inter request delays, to identify the user agent, and to collect no personally identifiable information, so that the data gathered is identical to what any visitor sees in a browser.

With a normalised catalogue being maintained automatically, the next question is how to surface relevant offers to individual users. The following section reviews the established paradigms for that task in the recommender systems literature.

\section{Recommendation Systems}

\subsection{Classification of Recommendation Approaches}

Recommendation systems are a class of information filtering tools that predict a user's preference for items based on available data \parencite{Geron2022, Raza2024Survey}. Closely related projects in the same mobile / telecommunications domain have repeatedly applied recommender techniques to mobile plan or mobile device catalogues: \textcite{ZhangLiu2011TCPRS} present the Telecom Product Recommender System (TCPRS), a hybrid user based / item based recommender for mobile products and services that helps new customers select the most suitable plan; \textcite{SoftZulu2017Zambia} describe a recommender system deployed in the Zambian telecom market that uses call detail records and demographic features to recommend products in a developing country context comparable to the Algerian one; and \textcite{Chandrahaas2023Mobile} present a recent (2023) hybrid recommender for mobile phones that combines content based filtering with collaborative filtering to handle exactly the content versus collaborative trade off discussed here. All three illustrate that the recommendation problem in this domain is real and tractable, and they confirm a recurring difficulty: at the start of a new aggregator's lifecycle, the user interaction history that the collaborative filtering paradigm depends on is not yet available, which forces an alternative approach.

{\sloppy Recent systematic reviews confirm that this picture has not changed in 2024--2025. \textcite{PoniszewskaMaranda2025} review thirty eight publications spanning 2013--2025 covering e commerce recommender systems and find content based filtering, collaborative filtering, and hybrid models still dominant; \textcite{Raza2024Survey} reach the same conclusion in a broader 2017--2024 review of the field. The choice of paradigm therefore turns on the data signal a system actually has, which is exactly the dimension the literature uses to classify recommender systems. The literature distinguishes three main paradigms whose characteristics are summarised in Table~\ref{tab:recsys-paradigms}.\par}

For any system launching without an interaction history, Table~\ref{tab:recsys-paradigms} narrows the choice sharply: collaborative filtering, and the hybrid path that depends on it, requires precisely the behavioural signal that is absent at launch, the cold start condition \parencite{AdomaviciusTuzhilin2005, hu2008collaborative}, whereas content based filtering operates on item attributes and an explicitly declared user profile, both available from the first day of operation. The hybrid path becomes available only once interaction data has accumulated.

\subsection{Multi Criteria Ranking and the Cold Start Problem}

When an item catalogue is small, fully enumerable, and described by well defined numerical attributes (for instance price, data, voice, and SMS), a content based approach is both appropriate and computationally efficient, and it requires no historical interaction data \parencite{Geron2022, LopsGemmisSemeraro2011}. The difficulty such a setting raises is not retrieval but \emph{ordering}: how to rank candidate items when a user holds several, possibly competing, preferences at once.

Selecting and ordering the best alternatives against several criteria at once is the subject of \textbf{multi criteria decision making} (MCDM), whose methods are catalogued in recent surveys \parencite{TaherdoostMadanchian2023}. The simplest, the weighted sum or \emph{simple additive weighting} model, scores each item as a weighted sum of its criterion values; it is easy but sensitive to how the raw scales are combined and offers no explicit target to aim at. A more robust and widely used method is \textbf{TOPSIS} (Technique for Order of Preference by Similarity to Ideal Solution): each alternative is scored by its \emph{Euclidean distance} to an ideal solution (the best value on every criterion) and to an anti ideal solution (the worst on every criterion), then ranked by a closeness coefficient in $[0,1]$ that is high when the alternative is near the ideal and far from the anti ideal. Introduced by \textcite{HwangYoon1981} and consolidated in recent comprehensive reviews \parencite{TaherdoostMadanchian2023}, TOPSIS handles several quantitative criteria simultaneously, returns a bounded score, and is content based, so it needs no interaction history. A recurring practical question is how to obtain the criterion \emph{weights} it requires: when a user can rank the criteria by importance but cannot quantify them, the \textbf{rank order centroid} (ROC) method converts that ranking into numeric weights, and is the most accurate of the simple rank based weighting formulae \parencite{BarronBarrett1996}. Methods that forbid any compensation between criteria, such as lexicographic ordering \parencite{Fishburn1974, Roberts1979}, are the alternative when one criterion must dominate absolutely; the trade off is between that strictness and the smoother, distance based discrimination of TOPSIS. Multi criteria recommendation remains an active research area: \textcite{JannachAbdollahpouri2023} survey multi objective recommender systems, and \textcite{ParkYooShin2025}, at the ACM Web Conference 2025, present a criteria aware graph filtering approach that treats user preferences as several separable dimensions rather than a single composite score, confirming that the multi criteria framing is current state of the art.

The absence of historical interaction data, the \emph{cold start} problem, is itself a well studied subfield of recommender systems. E commerce platforms face a continuous cold start problem when their catalogue and customer base evolve faster than usage signals accumulate \parencite{BernardiKamps2016}, and the most recent comprehensive survey of the problem reviews 220 papers and confirms that content based filtering with explicit user declared preferences remains the dominant response when interaction signals are not yet available \parencite{ZhangColdStart2025}. Taken together, a distance based MCDM ranking such as TOPSIS and content based filtering form a coherent response to the joint constraint of competing user priorities and absent behavioural history.

Recommendation answers the question \guillemotleft{}which item suits my declared profile?\guillemotright{} A complementary query, \guillemotleft{}which items match this free text description?\guillemotright{}, defines the search problem, reviewed in the next section.

\section{Search Engines}

A search engine is a software system that retrieves, from a body of content, the items most relevant to a user supplied query. The information retrieval literature distinguishes three broad families of search engine, each addressing a different content shape:

\begin{enumerate}
  \item \textbf{Web search engines} (Google, Bing) crawl the open Web and rank billions of unstructured pages against natural language queries, relying on link analysis, behavioural signals, and recent large language model layers.
  \item \textbf{Enterprise full text search engines} (Elasticsearch, Apache Solr, Meilisearch) index a defined corpus of documents and serve them through BM25 style ranking with facets, typo tolerance, and language aware tokenisation.
  \item \textbf{Structured product search} retrieves items from a fixed catalogue of records whose attributes are known in advance (price, category, brand, specifications); the dominant retrieval mode here is the typed, attribute driven query rather than the free text query of the first two families.
\end{enumerate}

Structured product catalogues belong squarely to the third family. \textcite{ChenWANDS2022} present, at the European Conference on Information Retrieval, the WANDS benchmark for product search relevance: 480 queries against a 43\,000 product Wayfair catalogue. Their results confirm that the dominant trade off facing a search feature designer is between \emph{relevance ranking} (which the user feels as result quality) and \emph{operational complexity} (which the engineer absorbs as build and maintenance cost). Two complementary academic perspectives further refine this trade off. \textcite{Vandic2024Faceted}, in \textit{Data \& Knowledge Engineering}, develop a framework for approximate product search through faceted navigation combined with user preference ranking: they show that for structured product offers, the natural retrieval model is a typed, attribute driven query rather than a free text full text search, because the attributes themselves carry the bulk of the search semantics. \textcite{AliCaputo2023Facet} provide a comprehensive survey of facet ranking approaches in faceted search systems and confirm that for catalogues whose items are described by a small, stable set of attributes, the appropriate retrieval model maps typed query tokens onto those attributes directly.

For very large free text catalogues the relevance gain of an industrial BM25 engine clearly justifies its operational cost; at the opposite end of the scale, a small catalogue of a few hundred fully structured items, the same trade off can flip in favour of a far simpler approach. Three implementation options are commonly considered when adding a search feature to a structured product catalogue. Table~\ref{tab:search-families} summarises their characteristics.

For a small catalogue of structured items whose attributes are known in advance (price, data volume, network, type, brand), Table~\ref{tab:search-families} resolves to a clear conclusion along the operational cost axis. Vendor published comparative analyses of the three families consistently report that industrial full text engines such as Elasticsearch require a dedicated indexing service and substantial configuration before they reach instant search latencies, that Meilisearch closes much of that gap at the cost of a separate process to operate, and that managed services such as Algolia charge a recurring per request fee \parencite{MeilisearchComparison2025}. An industrial engine therefore adds a second source of truth that must be kept synchronised; a managed service adds a recurring fee; whereas a hand rolled structured parser, mapping typed query tokens directly onto the database columns, adds no operational cost beyond the existing application stack. For a small structured catalogue with little genuinely free text querying, the operational cost criterion alone separates the families decisively in favour of the lightweight typed parser approach. Where some free text relevance is still wanted, the embedded full text index that many relational databases now ship, providing BM25 ranking, prefix matching, and Unicode aware tokenisation, can complement the parser without introducing a separate engine \parencite{SQLiteFTS5}.

Beyond these four core disciplines, a consumer facing comparison platform rests on three further concerns: how the collected offers are presented and compared, how users are kept informed when the catalogue changes, and how the interface is delivered across devices. The next three sections review each in turn.

\section{Comparison and Data Visualization}

Once candidate items have been retrieved and ranked, the user must still \emph{compare} them and read the result; the information design literature treats this as a problem distinct from retrieval. For structured products the established presentation pattern is the \textbf{comparison table}, a grid that places items in columns and their attributes in rows so that differences can be scanned down each row. Usability research identifies it as the standard, most legible device for comparing products, services, and features, provided the number of items and attributes on screen is kept small \parencite{NielsenComparisonTables}. To reduce a large catalogue to that comparable handful, \emph{faceted filtering}, selecting on attribute values such as price range, data volume, or network, is the dominant interaction pattern for structured catalogues \parencite{Vandic2024Faceted, AliCaputo2023Facet}.

Beyond the table, per attribute \emph{data visualization} lets a reader judge magnitude at a glance. The visualization literature gives well established encodings for this: position and length, the channels used by bar charts, are among the most accurately perceived for comparing quantitative values, a principle codified in modern visualization design frameworks \parencite{Munzner2014}. When items are not merely compared but \emph{ranked} on several attributes at once, \textcite{Gratzl2013LineUp} present, in the IEEE visualization literature, the LineUp technique for the visual analysis of multi attribute rankings, showing how to make visible both the overall order and the per attribute contributions that produce it. Together these results define how a small set of structured options should be filtered, tabulated, charted, and explained.

A complementary concern is keeping the user informed once that catalogue changes; the next section reviews notification systems.

\section{Notification Systems}

A notification system informs a user, asynchronously, of events that occurred without their direct request: a new item, a changed price, a newly relevant match. Two bodies of research bear on its design. Architecturally, the canonical model is \textbf{publish/subscribe}: consumers register (subscribe to) the kinds of event they care about, and the system delivers (publishes) matching events to them, without the producer and consumer being directly coupled. \textcite{Eugster2003PubSub}, in their widely cited ACM Computing Surveys article, map the variants of this paradigm, topic based, content based, and type based, and the decoupling in time, space, and synchronisation that makes it well suited to event driven applications.

From a human computer interaction standpoint a notification is an interruption, and the design challenge is to deliver useful information without imposing an excessive \emph{attention cost}. \textcite{McCrickardChewar2003}, in Communications of the ACM, frame notification design as a deliberate trade off between the user's primary task and the value of the interruption, and warn against the over notification that erodes trust and produces alert fatigue. The two perspectives combine into one guideline: subscribe users only to events matching their declared interests, and surface those events sparingly and in context.

How that interface reaches the user across the devices they own is the subject of the final section.

\section{Responsive Design and Accessibility}

A web application is consumed on screens ranging from a narrow phone to a wide desktop, and by users with a range of abilities; two established bodies of practice address this. \textbf{Responsive web design}, introduced by \textcite{Marcotte2011}, builds a single layout that adapts fluidly to the viewport through three techniques, fluid grids, flexible images, and CSS media queries, so that the same markup serves every device without a separate mobile site. \textbf{Web accessibility} is codified by the World Wide Web Consortium in the Web Content Accessibility Guidelines, whose current version organises its requirements under four principles, that content be perceivable, operable, understandable, and robust \parencite{WCAG22}. Together, responsive layout and conformance to these guidelines are what allow a single interface to remain usable on desktop, tablet, and mobile, and by the widest possible audience.

With these technical foundations mapped, the chapter now turns to the specific market in which they are applied: the Algerian mobile telecommunications sector.

\section{The Algerian Mobile Telecommunications Market}

\subsection{Market Overview and Key Figures}

Algeria's mobile telecommunications sector is regulated by the Autorité de Régulation de la Poste et des Communications Électroniques (ARPCE). According to ARPCE's most recent quarterly observatory, the country counts more than 54~million mobile subscribers in the first quarter of 2025, a 4.4\,\% increase over the same quarter of the previous year, distributed across three licensed operators: Mobilis, owned by the state controlled Algérie Télécom group; Djezzy, majority owned by VEON; and Ooredoo, a subsidiary of the Qatari group Ooredoo \parencite{ARPCE2025, ARPCE2024, Statista2024}. Mobile penetration stands at approximately 106\,\%, reflecting a mature market where many users hold multiple SIM cards.

The network infrastructure has evolved considerably over the past decade. Following the deployment of 4G LTE services in 2016, all three operators have expanded coverage progressively across the country. Djezzy launched commercially limited 5G trials in 2024, positioning itself as the first operator to test fifth generation technology in Algeria \parencite{GSMA2024}. These developments have accelerated the diversification of plan offerings, as operators compete on price, data volume, and network quality.

\subsection{Offer Complexity and the Consumer Decision Problem}

Each operator publishes a catalogue of prepaid, postpaid, and data only plans that is updated several times per year. Prices range from a few hundred to several thousand Algerian Dinars per month, depending on the included data volume (from 1~GB to over 200~GB), voice minutes (from limited bundles to unlimited calls), SMS allowances, and validity periods (daily, weekly, monthly, or longer). A consumer wishing to identify the most cost effective plan for their specific usage profile must visit three separate websites, compare offerings across heterogeneous formats, and account for promotional periods that may alter the base price.

\section{Existing Comparison Platforms}

Several international platforms have successfully addressed the plan comparison problem in their respective markets, and one Algerian multi vertical comparator addresses part of the same need locally. This section reviews both and then positions \textit{Mobile Match Algeria} against them.

\paragraph{International benchmarks.}
An analysis of three established international platforms reveals common features, architectural patterns, and limitations that inform the design of the present work.

\textbf{MonPetitForfait} (France, founded 2013) is an independent French aggregator that covers all four national operators (Orange, Bouygues Télécom, SFR, Free Mobile) plus a wide set of virtual operators (RED by SFR, B\&YOU, Sosh, Prixtel, and others). It provides a tabular comparison interface, a plan finder questionnaire, and user reviews. The platform relies primarily on operator partnerships and manual data entry rather than automated scraping, which limits how quickly its catalogue reflects operator side changes. It does not offer a personalisation engine beyond basic filtering \parencite{MonPetitForfait2026}.

\textbf{WhistleOut} (Australia and the United Kingdom) operates a comparison marketplace that includes both mobile plans and broadband. It features a strong search and filter interface and integrates affiliate referral links. Its data is updated through a combination of operator feeds and editorial review. The platform targets English speaking markets and its architecture is not publicly documented.

\textbf{CompareTheMobile} (United Kingdom) offers a highly visual comparison interface with side by side plan cards and a compatibility checker for handsets. Like its counterparts, it depends on voluntary operator data submission and does not employ automated collection.

\paragraph{An Algerian comparator: Comparili.net.}
One local platform was identified that addresses part of the same need. \textbf{Comparili.net}, founded in 2020 by three Algerian entrepreneurs, is a multi vertical comparator that covers business software (CRM, ERP, accounting), web hosting and online services, banking cards, and mobile telephony in a single WordPress based site \parencite{Comparili2024}. Mobile plans appear as one of several categories alongside the software and hosting verticals that dominate the platform's positioning (\guillemotleft{}le comparateur N\textsuperscript{o}1 des logiciels métiers informatiques\guillemotright{} according to its own home page). Its mobile plan section provides a filter based comparison of SIM card offerings supported by editorial articles and user reviews \parencite{Comparili2024}.

The existence of Comparili.net confirms that a market demand for comparison tools in Algeria is real and already partially served. It also delimits a clear positioning space for the present work. Mobile Match Algeria differs from Comparili.net along five axes:

\begin{itemize}
  \item \textbf{Scope}: Comparili.net is a multi vertical comparator with mobile plans as one section among many; Mobile Match Algeria is a dedicated mobile plan platform with a deeper feature set on that single vertical.
  \item \textbf{Data acquisition}: Comparili.net is editorially curated and enriched by user submitted reviews; Mobile Match Algeria relies on an automated scraping pipeline that synchronises offers from the three operator websites on a scheduled basis.
  \item \textbf{Personalisation}: Comparili.net offers filtering and a SIM comparison page; Mobile Match Algeria adds a multi criteria (TOPSIS) recommendation engine that orders offers by the user's declared budget, usage profile, and priority ranking.
  \item \textbf{Language}: Comparili.net is published in French; Mobile Match Algeria offers a trilingual interface (French, English, Arabic) to extend reach within the Algerian user base.
  \item \textbf{Openness}: Comparili.net is a proprietary WordPress platform; Mobile Match Algeria is open source and intended as both a consumer tool and an academic artefact.
\end{itemize}

\paragraph{Gap analysis for Algeria.}
Beyond Comparili.net, none of the international platforms identified above serve the Algerian market directly. The absence of additional comparators can be explained by several structural factors: the relatively small number of operators (three), the absence of virtual operators, and the lack of public APIs that would facilitate data integration. The international platforms reviewed rely on operator cooperation or affiliate relationships that do not exist in the Algerian context. Furthermore, none of these platforms, Comparili.net included, offers an Arabic language interface, which is essential for reaching the full Algerian user base, nor a deep multi criteria scoring recommendation engine tailored to mobile plan attributes.

\section{Positioning and Technology Choices of This Work}

The preceding review establishes that the only Algerian platform addressing this need, Comparili.net, covers mobile plans as one vertical among several and relies on editorial curation and user reviews rather than on automated aggregation. No \emph{dedicated} mobile plan platform with deep multi criteria features for Algerian consumers currently exists. The combination of scheduled automated data collection, a multi criteria (TOPSIS) recommendation engine with explicit priority ranking, a structured search interface, a savings calculator, a notification system, a multi language interface (English, French, Arabic), and a side by side comparison view distinguishes \textit{Mobile Match Algeria} from both the international platforms reviewed and from the local Comparili.net offering.

Having surveyed each discipline as pure research above, we now return to the project. After comparing the different tools the literature put forward, we selected one approach per discipline for \textit{Mobile Match Algeria}. For each discipline below we briefly recall the options that were on the table, then name the tool we chose and explain why it best fits the project's constraints.

\subsection{Web data aggregation and web scraping}

For data acquisition we chose web scraping over an API or feed integration, because no Algerian operator exposes a consumer facing plan API and the literature establishes scraping as the standard method for datasets published only as HTML \parencite{BoegershausenDatta2022, GlezPena2014}. Within scraping, we chose the dynamic real browser approach over static fetching, because at least one operator (Djezzy) rejects plain HTTP requests and a real browser is in any case robust to client side rendering, at a resource cost that is negligible for the handful of runs performed each day \parencite{Mitchell2018, KahlonSingh2026}. Concretely, we drive a real headless Microsoft Edge browser through Playwright to fetch each operator page, then parse the returned HTML with Cheerio; this is the lightest configuration that handles anti bot defences and JavaScript rendered layouts without a paid service. Each alternative was weighed on three axes: capability (does it solve a problem the chosen stack does not), integration cost (does it force a language or runtime switch from the TypeScript/Next.js base), and operational cost (does it require a paid service or commercial account). The scraped values are then normalised to a common schema (unit conversion from MB to GB, removal of promotional suffixes, numeric extraction, defaults for absent fields), and only publicly visible marketing pages are consumed, with rate limits respected, the user agent identified, and no personal data collected.

\subsection{Recommendation engine}

For recommendation we chose a content based design ranked by \textbf{TOPSIS} \parencite{HwangYoon1981, TaherdoostMadanchian2023}, with criterion weights derived from the user's ranking by the \textbf{rank order centroid} method \parencite{BarronBarrett1996}. The choice follows from the project's constraints. Collaborative filtering and the deep learning recommenders that dominate large platforms were excluded because they need an interaction history the aggregator does not have at launch, the cold start condition \parencite{AdomaviciusTuzhilin2005, ZhangColdStart2025}; TOPSIS, being content based, ranks from the plan attributes and the user's stated profile alone, so it works from the first day. We preferred TOPSIS over the plainer weighted sum because it ranks against an explicit ideal and anti ideal rather than an unbounded total, and over strictly non compensatory rules such as lexicographic ordering \parencite{Fishburn1974} because, for a consumer choosing a plan, a small price difference should not erase a large data advantage; TOPSIS lets the criteria trade off while the weights still encode the user's priority. Crucially, every step is a published formula, so nothing in the ranking is invented.

The engine first applies \emph{hard filters} (preferred operator, plan type, network generation, and the budget, a strict ceiling) to exclude incompatible offers, then ranks the survivors with TOPSIS over the criteria the user ranked (price and data by default):
\begin{enumerate}
  \item the user's ranking of the criteria becomes weights $w_j$ by the rank order centroid formula $w_k = \tfrac{1}{n}\sum_{i=k}^{n} \tfrac{1}{i}$ \parencite{BarronBarrett1996} (for two criteria this gives $0.75$ and $0.25$);
  \item each criterion column is vector normalised, $r_{ij} = x_{ij}/\sqrt{\sum_i x_{ij}^2}$, then weighted, $v_{ij} = w_j\, r_{ij}$ \parencite{HwangYoon1981};
  \item the ideal $A^{+}$ and anti ideal $A^{-}$ are formed, the minimum of a cost criterion such as price and the maximum of a benefit criterion such as data \parencite{HwangYoon1981};
  \item each offer's Euclidean distances to those two reference points, $S_i^{+} = \sqrt{\sum_j (v_{ij}-A^{+}_j)^2}$ and $S_i^{-} = \sqrt{\sum_j (v_{ij}-A^{-}_j)^2}$, give the closeness coefficient $C_i = S_i^{-}/(S_i^{+}+S_i^{-}) \in [0,1]$ \parencite{HwangYoon1981};
  \item offers are ranked by $C_i$ and the top three returned, with $C_i$ reported as the match score.
\end{enumerate}
Each formula above carries its reference at the step that uses it: the weighting is the rank order centroid of \textcite{BarronBarrett1996}, and the normalisation, the ideal points, and the closeness coefficient are the TOPSIS procedure of \textcite{HwangYoon1981}. The only project specific decisions are which criteria a user may rank and that the budget is a hard ceiling. The full algorithm with a worked example is in Chapter~3, Section~3.4.

\subsection{Search engine}

For search we chose a hand rolled token parser combined with SQLite's built in FTS5 full text index over an industrial or managed engine, because the catalogue is small and structured and an external engine would add operational cost and a second source of truth for no relevance gain at this scale \parencite{Vandic2024Faceted, MeilisearchComparison2025, SQLiteFTS5}. A small set of regular expressions extracts typed tokens (operator, data volume, price range, network, plan type, and feature keywords such as \guillemotleft{}unlimited\guillemotright{}) and translates them into a Prisma where clause; any words left over are routed to the FTS5 module, which provides BM25 relevance ranking, prefix matching, and Unicode aware tokenisation. Because FTS5 ships inside SQLite itself, its index lives in the same database file as the canonical Offer table and is rebuilt at scrape time, giving the relevance primitives of an industrial engine with no extra process to operate. The same parser also runs in the browser to render each query as \guillemotleft{}Read as\guillemotright{} chips, so the user sees exactly how their text was interpreted.

\subsection{Comparison and data visualization}

We present results through three established devices. Side by side, the selected plans are laid out in a \textbf{comparison table} (operators in columns, attributes in rows), the standard pattern for comparing structured products \parencite{NielsenComparisonTables}, kept to a few plans at a time. Each metric is also drawn as a \textbf{bar chart}, using the position and length encodings that the visualization literature identifies as the most accurate for quantitative comparison \parencite{Munzner2014, Gratzl2013LineUp}, and the catalogue is narrowed with \textbf{faceted filters} on operator, type, network, price, and data \parencite{Vandic2024Faceted}. A savings indicator, the remaining budget computed as budget minus price, is shown on each card. We chose a lightweight in browser charting library over a heavyweight business intelligence tool because the comparison spans only a handful of plans on a few numeric metrics, where the simplest faithful encoding is preferable.

\subsection{Notification system}

Users and administrators are kept informed through an in app notification stream modelled on the \textbf{publish/subscribe} pattern \parencite{Eugster2003PubSub}: each user is notified only of events that match their declared profile (a new offer, a price drop, a newly relevant match), while administrators receive operational events (a scrape completing or failing). Separating the two streams and matching each notification to a declared interest keeps the attention cost low and avoids the over notification that erodes trust \parencite{McCrickardChewar2003}. We chose an in app, database backed stream over external push or email services to avoid a third party dependency and keep the system self contained at this scale.

\subsection{Responsive and accessible interface}

The interface is built with \textbf{responsive web design} \parencite{Marcotte2011} so that one set of pages adapts to desktop, tablet, and mobile through fluid layout and CSS media queries, and it follows the \textbf{WCAG 2.2} accessibility guidelines \parencite{WCAG22} (semantic markup, keyboard navigation, sufficient contrast). We treat full WCAG conformance as an explicit goal rather than a verified result: a formal accessibility audit is left to future work.

\subsection{Application stack}

For the application itself we chose a contemporary full stack JavaScript stack centred on three pillars: Next.js 16 as a React based framework supporting server side rendering, the file system based App Router, and back end API routes inside the same project \parencite{NextJSDocs2024}; Prisma 7 as a type safe database toolkit whose single schema.prisma file is the unique source of truth for the data model and from which TypeScript types are auto generated \parencite{PrismaDocs2024}; and SQLite as a serverless, file based relational database that provides adequate performance and zero operational overhead at this scale. The full justification of these choices, together with the rejected alternatives (Nuxt, SvelteKit, TypeORM, Drizzle, PostgreSQL, MySQL), is developed in Chapter~2, Section~2.8.

In short, by studying the research and comparing the tools available for each discipline, we found that those named above are the best tools for this project. The following chapter translates the requirements identified in this review into a concrete system design.

\section{Chapter Summary}

This chapter has introduced the technical disciplines and design concerns that underpin \textit{Mobile Match Algeria}, web data aggregation, web scraping, recommendation systems, and search engines, then the comparison and visualization of results, notification systems, and responsive accessible delivery, and then situated those techniques within the Algerian mobile telecommunications market. The review of international comparison platforms together with the local multi vertical comparator Comparili.net confirmed the gap: no specialised mobile plan platform with automated data aggregation and a multi criteria recommendation engine currently exists for Algerian consumers. The final section stated the project's positioning relative to that landscape and, for each discipline and concern, the concrete technology chosen to implement it, real browser scraping with Playwright and Cheerio, a TOPSIS recommender with rank-order-centroid weights, a structured parser backed by SQLite FTS5, comparison tables and charts, a publish/subscribe notification stream, and a responsive accessible interface, on a Next.js, Prisma, and SQLite stack whose detailed justification follows in Chapter~2.
