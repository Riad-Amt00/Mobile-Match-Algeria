\chapter{Evaluation and Documentation}

The implementation described in Chapter~3 must now be evaluated against the project objectives, not merely described. This chapter answers four questions in sequence. \textbf{Did the project meet its objectives?} Section~4.1 maps each of the five FICHE deliverables to its concrete artefact and the evidence of completion. \textbf{Does the recommendation engine behave as specified?} Section~4.2 validates it analytically against four scenario tests drawn from the project's unit-test suite, including the iterative refinement that produced the final scoring model. \textbf{Does the system hold up under load?} Section~4.3 reports the production-build benchmarks measured on the offers, search, and recommendation endpoints. \textbf{Does the system respect user isolation?} Section~4.4 documents the multi-account functional testing performed. The chapter closes with an honest accounting of limitations in section~4.5 and a summary of the documentation produced in section~4.6, both of which feed directly into the Perspectives chapter that follows.

\section{Validation of the Recommendation Engine}

The recommendation engine is a deterministic function: given a fixed input profile and a fixed offer catalogue, it always produces the same ranked list. This property makes it possible to validate the engine analytically — by deriving the expected outcome from the engine's rules before running it, then checking that the actual output matches the prediction. Four scenario tests cover the key behavioural properties of the engine and are persisted as automated unit tests in \texttt{src/lib/\_\_tests\_\_/recommendation.test.ts}. Table~\ref{tab:rec-validation} reports each scenario, its analytically predicted outcome, the engine's actual output, and the resulting pass / fail verdict.

The four scenarios verify, respectively: the budget hard ceiling, the data-target coverage property, the tiered priority order (first priority strictly dominates the result, second priority refines within the tier), and the engine's behaviour when the user's constraints are unsatisfiable. The full test suite contains ninety-nine unit tests across the recommendation engine and the scraping parsers; all tests pass at the time of writing.

\subsection{Iterative Refinement of the Scoring Model}

The validation tests above are passed by the tiered-ranking model described in Chapter~3, but four earlier scoring models were rejected during development on the basis of the same scenarios. The most informative failure mode was that of the weighted-mean models: although they could pass the budget and data scenarios individually, neither weighted arithmetic mean nor weighted geometric mean ever produced the clean \guillemotleft{}primary-then-secondary\guillemotright{} order required by the third scenario, because a strong score on the secondary criterion was systematically allowed to compensate for a poor score on the primary. The tiered-ranking model resolves this by enforcing a strict partition of the offer space along the primary priority, with the secondary priority restricted to ordering within each partition.

\section{Performance Benchmarks}

To characterise the platform's capacity, the application was built in production mode (\texttt{npm run build} followed by \texttt{npm start}) and exercised with synthetic load using a concurrent-worker harness written in plain Node.js. Three endpoints were tested under increasing concurrency (one, ten, fifty, and one-hundred concurrent workers) over a ten-second window each. The rate-limit cap on \texttt{/api/recommendations} was bypassed during benchmarking by varying the \texttt{X-Forwarded-For} header per request; in production this cap remains a real safety brake against abuse. The platform sustains zero errors at every concurrency level, on every endpoint. The browse endpoint serves more than two hundred requests per second under fifty-way concurrent load; the structured-search endpoint is faster than browse, because the search filter prunes rows in Prisma so that fewer are serialised back. The recommendation endpoint plateaus at approximately sixty requests per second, which corresponds to the engine's CPU-bound work: hard filtering, merit computation, tier assignment, sorting, and slicing. At the current scale of a few active users, the slowest endpoint alone offers roughly thirty times the realistic peak load, providing comfortable operational headroom. These results characterise the single-machine behaviour; performance on a deployed cloud platform would depend on the host's CPU profile and is identified as a benchmarking direction in Perspectives.

\section{Functional Testing in a Multi-Account Configuration}

The system was exercised in a multi-account configuration to verify that user isolation is correctly enforced across all stateful features. Four accounts (one administrator, one demo account from the seed, and two test accounts) were created and used concurrently from a single development machine. The verification covered four properties: session isolation (signing in as one account never exposes another account's session), profile separation (one account's \texttt{UserProfile} is never returned for another user), saved-plans separation (one account's \texttt{SavedOffer} list is never visible to another), and notification separation (administrator-stream notifications never appear in a non-admin user's notification list, and conversely). No leakage was observed in any of these dimensions. This functional verification is complementary to, and does not substitute for, the formal usability study with end users that is identified in the Perspectives section.

The four evaluation axes covered so far --- objectives achievement, engine validation, load characterisation, and multi-account isolation --- all return positive results within their scope. Honesty requires the chapter to also account for what is \emph{not} achieved or not yet measured; the next section enumerates the limitations identified.

\section{Limitations}

Six identifiable limitations should be acknowledged in the current version of \textit{Mobile Match Algeria}.

The first limitation is the \textbf{scalability ceiling of SQLite}. SQLite is a single-file, serverless database that does not support concurrent writes. For the current single-server deployment, this is not a practical constraint and is supported by the load-test results in Section~4.3. A migration to PostgreSQL would be required before the platform could support horizontal scaling or sustained high write concurrency. Prisma supports both engines, so the migration is essentially a configuration change at the application level.

The second limitation is the \textbf{fragility of web scrapers}. The scraping module parses the DOM structure and CSS class names of operator websites, which can change at any time without notice. A change in an operator's website layout would render the corresponding scraper non-functional until it is manually updated. Empirically, over the 208 scrape runs persisted in the \texttt{ScrapeLog} table at the time of writing, \textbf{95.7\,\% completed with status \texttt{SUCCESS}} and \textbf{2.9\,\% with status \texttt{FAILED}}; the snapshot-based unit tests in \texttt{src/lib/scraper/\_\_tests\_\_} detect parser regressions as soon as a snapshot diverges from the live page, and the audit trail provides operational visibility for the remaining failures, but the maintenance burden remains real.

The third limitation concerns the \textbf{flattened \guillemotleft{}unlimited\guillemotright{} scope}. The database currently models calls and SMS as binary attributes ($-1$ for unlimited, $0$ for none). Real operator offers, however, distinguish between unlimited on-net (\guillemotleft{}illimité vers Djezzy\guillemotright{}) and unlimited all-networks. This finer scope is preserved in each offer's feature text and shown to the user, but it is not a separate scoring dimension. Treating calls and SMS as binary filters reflects the structurally binary way Algerian operators bundle them in the published catalogues; refining this into a scoped attribute is identified in Perspectives.

The fourth limitation concerns the \textbf{search engine's matching behaviour}. The hand-rolled parser is deliberately strict: it requires substring matches with no typo tolerance, so a query mistyped as \guillemotleft{}djezy\guillemotright{} returns no result. It does not implement BM25-style relevance ranking, so an offer whose name contains the query and an offer whose buried feature text contains the same query are ranked equally. Accented characters are not folded reliably because SQLite's \texttt{LIKE} operator is case-insensitive only for ASCII. The example-chip presets and the visible \guillemotleft{}Read as\guillemotright{} chips mitigate these limitations by giving the user known-good queries to start from, but a transition to a BM25 engine such as Meilisearch is the natural extension if catalogue scale or vocabulary diversity grows.

The fifth limitation is the \textbf{absence of a formal user study}. The validation reported in this chapter is technical: it confirms that the engine correctly implements its own rules, that the system sustains load without errors, and that user isolation is enforced. It does not measure whether the platform's recommendations match real users' subjective preferences or whether the interface is intuitive for first-time users. A formal usability study with approximately fifty external testers — using a standard instrument such as the System Usability Scale \parencite{NielsenNorman2023} — is the first item listed in the Perspectives section.

The sixth limitation is the \textbf{single-machine evaluation deployment}. The platform is built and exercised in production mode locally and demonstrated on the development machine. Public deployment to a managed cloud host has not been performed within the project timeline and is identified as a perspective; the architecture (Next.js application, Prisma ORM, file-based SQLite database) is portable to standard Node.js hosting platforms without code changes.

These six limitations feed directly into the Perspectives chapter that follows the general conclusion. Before turning to perspectives, the next section accounts for the documentation produced alongside the system itself, since the deliverables of the project include more than just running code.

\section{Documentation}

The project ships four documentation artefacts, each addressing a different audience.

\paragraph{User guide.} Integrated into the running application as the \texttt{/help} page accessible from the main navigation bar. It is organised into five sections --- search, recommendations, comparison, filters, and saved plans --- each containing a textual description, numbered step-by-step instructions, annotated screenshots captured automatically from the live application, and a link to the corresponding page. Sections requiring authentication carry a \guillemotleft{}sign-in required\guillemotright{} badge.

\paragraph{Administrator manual.} Covers the admin-dashboard workflows: triggering scrape runs, reading scrape logs, interpreting operator-health status indicators, managing notifications, and monitoring platform statistics. It also documents the environment-variable configuration (\texttt{DATABASE\_URL}, \texttt{NEXTAUTH\_SECRET}, \texttt{NEXTAUTH\_URL}, \texttt{ADMIN\_CLAIM\_CODE}), the one-time admin-claim flow, and the procedure for running the scraper in manual mode via the command line.

\paragraph{API reference.} A concise route-level reference is provided as Table~3.2 in Chapter~3. For each route, it lists the HTTP methods, the required authentication, the accepted query parameters or request-body fields, and the rate-limit policy where applicable. This reference facilitates future development and potential integration with third-party clients.

\paragraph{Source-code repository.} The complete source code, the LaTeX source of this mémoire, and the regeneration scripts for the figures and screenshots are publicly available at \url{https://github.com/Riad-Amt00/Mobile-Match-Algeria}. The repository's \texttt{README.md} carries the installation and run instructions, the demo accounts seeded by \texttt{prisma/seed.ts}, the environment variables expected by the application, and the build commands for both the Next.js application and the LaTeX mémoire. The directory layout follows standard Next.js conventions (\texttt{src/app/}, \texttt{src/lib/}, \texttt{prisma/}, \texttt{public/}), with \texttt{memoire/} for the present document and \texttt{scripts/} for auxiliary database-audit and user-deletion utilities.

\section*{Chapter Summary}

This chapter has evaluated \textit{Mobile Match Algeria} against the five project objectives defined in the subject fiche, validated the recommendation engine on four scenario tests covering the budget ceiling, data coverage, tiered priority order, and the empty-result edge case, reported the load-testing results showing zero errors and over two hundred requests per second on the browse endpoint, and described the multi-account functional testing performed. The six limitations identified — SQLite scalability, scraper fragility, the flattened unlimited scope, the strictness of the search parser, the absence of a formal user study, and the single-machine evaluation deployment — provide a clear roadmap for the improvements outlined in the general conclusion that follows.
