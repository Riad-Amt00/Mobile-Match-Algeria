\chapter{Evaluation}

The implementation described in Chapter~3 must now be evaluated against the project objectives, not merely described. This chapter answers three questions in sequence. \textbf{Did the project meet its objectives?} Section~4.1 maps each of the five FICHE deliverables to its concrete artefact and the evidence of completion. \textbf{Does the recommendation engine behave as specified?} Section~4.2 validates it analytically against four scenario tests drawn from the project's unit test suite. \textbf{Does the system respect user isolation?} Section~4.3 documents the multi account functional testing performed across isolated user sessions.

\section{Validation of the Recommendation Engine}

The recommendation engine is a deterministic function: given a fixed input profile and a fixed offer catalogue, it always produces the same ranked list. This property makes it possible to validate the engine analytically, by deriving the expected outcome from the engine's rules before running it, then checking that the actual output matches the prediction. Four scenario tests cover the key behavioural properties of the engine and are persisted as automated unit tests in src/lib/\_\_tests\_\_/recommendation.test.ts. Table~\ref{tab:rec-validation} reports each scenario, its analytically predicted outcome, the engine's actual output, and the resulting pass / fail verdict.

The four scenarios verify, respectively: the budget hard ceiling, the data target coverage property, the priority weighting (the criterion ranked first is weighted most by rank order centroid and dominates the TOPSIS ranking, the second criterion ordering the rest), and the engine's behaviour when the user's constraints are unsatisfiable. The full test suite contains one hundred and twenty one unit tests across the recommendation engine, the scraping parsers, the structured search parser, and the formatting utilities; all tests pass at the time of writing.

\subsection{Method Selection}

The validation tests above are passed by the TOPSIS ranking described in Chapter~3. TOPSIS was selected over the alternatives considered against the same scenarios. A plain weighted mean (arithmetic or geometric) was set aside because it yields an unbounded score and lets a strong secondary criterion compensate for a weak primary one, blurring the user's stated priority; a strictly non compensatory lexicographic rule was set aside because it lets a negligible price difference erase a large data advantage, too rigid for a consumer plan choice. TOPSIS keeps the criteria trading off smoothly while the rank order centroid weights still encode the user's ranking, and it reports a bounded closeness score. The full method comparison is in Chapter~3, Section~3.4.

\section{Functional Testing in a Multi Account Configuration}

Because the platform stores a personal profile, a list of saved plans, and a private notification stream for every registered user, a defect that allowed one account's data to surface in another account's session would be both a privacy breach and a correctness failure. The system was therefore exercised in a deliberate multi account configuration whose only purpose was to confirm that user isolation holds across every stateful feature, not merely on the screen that displays the data but in the API responses that feed it.

Four accounts were provisioned and driven concurrently from separate browser sessions on a single development machine: one administrator, one demo account loaded from the seed script, and two ordinary test accounts. Operating them in parallel, rather than one after another, is what makes the test meaningful, because it reproduces the realistic situation in which several authenticated requests are in flight at once and a server side mistake, such as a query missing its user filter or a shared session token, would let one account observe another's data.

The verification covered four isolation properties. Session isolation requires that signing in as one account never exposes another account's session or identity. Profile separation requires that one account's profile is never returned in another user's request, so the recommendation engine always reads the correct budget and usage profile. Saved plans separation requires that one account's saved list is never visible to, or modifiable by, another account. Notification separation requires that administrator stream notifications, such as scrape completed or scrape failed, never reach an ordinary user, and that a user's personal notifications, such as a new offer, a price drop, or a recommendation, never reach a different user. Each property was checked both in the rendered interface and in the raw API responses behind it, and no leakage was observed in any of the four dimensions.

This functional verification confirms that the access control and the per user data scoping behave as designed. It is complementary to, and does not substitute for, the formal usability study with end users that is identified in the Perspectives section.

The three evaluation axes covered above, objectives achievement, engine validation, and multi account isolation, all return positive results within their scope.
