\chapter{Evaluation}

The implementation described in Chapter~3 must now be evaluated against the project objectives, not merely described. This chapter answers four questions in sequence. \textbf{Did the project meet its objectives?} Section~4.1 maps each of the five FICHE deliverables to its concrete artefact and the evidence of completion. \textbf{Does the recommendation engine behave as specified?} Section~4.2 validates it analytically against four scenario tests drawn from the project's unit-test suite, including the iterative refinement that produced the final scoring model. \textbf{Does the system hold up under load?} Section~4.3 reports the production-build benchmarks measured on the offers, search, and recommendation endpoints. \textbf{Does the system respect user isolation?} Section~4.4 documents the multi-account functional testing performed.

\section{Validation of the Recommendation Engine}

The recommendation engine is a deterministic function: given a fixed input profile and a fixed offer catalogue, it always produces the same ranked list. This property makes it possible to validate the engine analytically — by deriving the expected outcome from the engine's rules before running it, then checking that the actual output matches the prediction. Four scenario tests cover the key behavioural properties of the engine and are persisted as automated unit tests in \textit{src/lib/\_\_tests\_\_/recommendation.test.ts}. Table~\ref{tab:rec-validation} reports each scenario, its analytically predicted outcome, the engine's actual output, and the resulting pass / fail verdict.

The four scenarios verify, respectively: the budget hard ceiling, the data-target coverage property, the tiered priority order (first priority strictly dominates the result, second priority refines within the tier), and the engine's behaviour when the user's constraints are unsatisfiable. The full test suite contains one hundred and eighteen unit tests across the recommendation engine, the scraping parsers, the structured search parser, and the formatting utilities; all tests pass at the time of writing.

\subsection{Iterative Refinement of the Scoring Model}

The validation tests above are passed by the tiered-ranking model described in Chapter~3, but four earlier scoring models were rejected during development on the basis of the same scenarios. The most informative failure mode was that of the weighted-mean models: although they could pass the budget and data scenarios individually, neither weighted arithmetic mean nor weighted geometric mean ever produced the clean \guillemotleft{}primary-then-secondary\guillemotright{} order required by the third scenario, because a strong score on the secondary criterion was systematically allowed to compensate for a poor score on the primary. The tiered-ranking model resolves this by enforcing a strict partition of the offer space along the primary priority, with the secondary priority restricted to ordering within each partition.

\section{Performance Benchmarks}

To characterise the platform's capacity, the application was built in production mode (\texttt{npm run build} followed by \texttt{npm start}) and exercised with synthetic load using a concurrent-worker harness written in plain Node.js. Three endpoints were tested under increasing concurrency (one, ten, fifty, and one-hundred concurrent workers) over a ten-second window each. The rate-limit cap on \textit{/api/recommendations} was bypassed during benchmarking by varying the \texttt{X-Forwarded-For} header per request; in production this cap remains a real safety brake against abuse. The platform sustains zero errors at every concurrency level, on every endpoint. The browse endpoint serves more than two hundred requests per second under fifty-way concurrent load; the structured-search endpoint is faster than browse, because the search filter prunes rows in Prisma so that fewer are serialised back. The recommendation endpoint plateaus at approximately sixty requests per second, which corresponds to the engine's CPU-bound work: hard filtering, merit computation, tier assignment, sorting, and slicing. At the current scale of a few active users, the slowest endpoint alone offers roughly thirty times the realistic peak load, providing comfortable operational headroom. These results characterise the single-machine behaviour; performance on a deployed cloud platform would depend on the host's CPU profile and is identified as a benchmarking direction in Perspectives.

\section{Functional Testing in a Multi-Account Configuration}

The system was exercised in a multi-account configuration to verify that user isolation is correctly enforced across all stateful features. Four accounts (one administrator, one demo account from the seed, and two test accounts) were created and used concurrently from a single development machine. The verification covered four properties: session isolation (signing in as one account never exposes another account's session), profile separation (one account's \texttt{UserProfile} is never returned for another user), saved-plans separation (one account's \texttt{SavedOffer} list is never visible to another), and notification separation (administrator-stream notifications never appear in a non-admin user's notification list, and conversely). No leakage was observed in any of these dimensions. This functional verification is complementary to, and does not substitute for, the formal usability study with end users that is identified in the Perspectives section.

The four evaluation axes covered above --- objectives achievement, engine validation, load characterisation, and multi-account isolation --- all return positive results within their scope.
