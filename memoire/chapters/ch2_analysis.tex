\chapter{Requirements Analysis and System Design}

Building on the state of the art surveyed in Chapter~1, this chapter formalises the requirements of \textit{Mobile Match Algeria} and presents the architectural and design decisions taken to meet them. The chapter covers requirements gathering, actor identification, UML modelling, data model definition, system architecture, UI/UX principles, and technology stack justification.

\section{Requirements Gathering}

\subsection{Methodology — Secondary Documentary Research}

The needs-analysis phase of this project follows a documentary-research methodology grounded in the official publications of the Algerian telecommunications sector, supplemented by one regional report. Three country-specific sources form the primary foundation:

\begin{itemize}
  \item The \textbf{ARPCE annual report and quarterly observatories on the Algerian telecommunications market} (the national regulator) provide the most current subscriber counts (more than 54~million mobile subscribers in Q1 2025), the market shares of the three operators, average revenue per user, and the breakdown of prepaid and postpaid subscriptions \parencite{ARPCE2025, ARPCE2024}.
  \item The \textbf{DataReportal \textit{Digital 2025: Algeria}} country survey provides the average monthly mobile-data consumption per user, the time spent on mobile services, and the internet-penetration figures specific to Algeria \parencite{DataReportal2025}.
  \item The \textbf{Mordor Intelligence Algeria Telecom Market} sectoral analysis covers the 2025--2030 outlook for the Algerian market, with growth projections and competitive dynamics \parencite{Mordor2025}.
\end{itemize}

These three country-specific reports are complemented by the \textbf{GSMA Intelligence \textit{Mobile Economy MENA}} report \parencite{GSMA2024}, used here as a regional reference for the 4G and 5G penetration rates and the smartphone-adoption trend, with Algeria appearing as one country within the MENA aggregate. GSMA is deliberately positioned as a supplement rather than a primary source because its analysis is regional rather than national, and the country-specific reports above are the load-bearing references for the needs-analysis claims.

These secondary indicators substitute for a primary user survey within the project timeline and provide a defensible, citable empirical foundation for the requirement set. A complementary structural analysis of the three operator websites (Mobilis, Djezzy, Ooredoo) and of the international comparison platforms reviewed in Chapter~1 was conducted to identify the information currently exposed to consumers and the user-interface conventions established by the comparison-platform domain. A formal usability study with end users is acknowledged as a limitation of this work and is proposed in the Perspectives chapter.

The pipeline begins when a cron trigger or administrator action initiates a scrape for a given operator. The scraper fetches the operator's plan page, parses and normalises the data, and compares each scraped offer against the existing database entries. New offers are inserted; existing offers with changed attributes are updated; offers absent from the scraped data are marked inactive. A ScrapeLog record is created regardless of outcome, recording the number of offers found, inserted, updated, and any error encountered.

The client sends a POST request to \texttt{/api/recommendations} with the user's profile parameters. The API server validates the session token, retrieves all active offers from the database, passes the offer list and user profile to the recommendation engine, and returns the top three scored results. The entire server-side operation is stateless and completes in under 100~ms for the current catalogue size.

\section{System Architecture}

\subsection{Three-Tier Architecture}

The application follows a classic three-tier architecture. The \textbf{presentation tier} consists of React components rendered by Next.js, either on the server (for initial page load) or on the client (for interactive elements). The \textbf{logic tier} consists of Next.js API route handlers located in the \texttt{src/app/api/} directory, which implement the business logic and data access layer. The \textbf{data tier} consists of a SQLite database accessed exclusively through Prisma.

The UI/UX principles that follow are the user-side counterpart to this contract.

\section{UI/UX Design}

\subsection{Design Principles}

The interface design of \textit{Mobile Match Algeria} is guided by five principles. First, \textbf{clarity}: information hierarchy is conveyed through typographic weight and spatial grouping rather than decorative elements, so users can locate the data they need at a glance. Second, \textbf{feedback}: every user action — saving a plan, comparing, triggering a scrape — produces an immediate visual response (toast notification, button state change, loading indicator). Third, \textbf{consistency}: the same card component, the same filter pills, and the same button styles appear throughout the application, reducing the cognitive load of navigation. Fourth, \textbf{responsiveness}: the interface reflows gracefully from 320~px mobile widths to wide desktop screens using CSS Grid and flexbox. Fifth, \textbf{accessibility}: interactive elements are keyboard-navigable and colour contrast ratios meet the WCAG~2.1 AA standard.

\subsection{Key Interface Screens}

The application comprises nine main screens, whose appearance is illustrated by the screenshots embedded in Chapter~3, Section~3.8.

\begin{enumerate}
  \item \textbf{Home page} — Language-selection landing page presenting feature highlights and operator logos. Authenticated users are redirected directly to the offers page.
  \item \textbf{Offers page} — Grid of offer cards with operator filter tabs, plan-type pills, an advanced filter panel (price, data, network), and a structured search input above the grid that displays parsed query tokens as chips. A sticky bottom bar appears when plans are selected for comparison.
  \item \textbf{Comparison page} — Side-by-side table together with per-metric bar charts (price and data volume) for the selected plans, plus an annual-savings bar chart when the comparison was launched from the recommendations page.
  \item \textbf{Recommendations page} — Usage-profile form (budget, data, voice, SMS toggles, plan type, network, operator, ranked priorities) and the ranked list of three matched plans displayed with rank badges; each ranked card carries an integrated savings indicator showing the monthly, annual, and percentage saving obtained by switching to that plan from the user's monthly budget.
  \item \textbf{Saved-plans page} — Grid of plans bookmarked by the user, with a direct path to the comparison view and per-card removal.
  \item \textbf{Help / tutorial page} — Five sections (search, recommend, compare, filters, saved) each containing a description, step-by-step instructions, annotated screenshots, and a link to the corresponding page. Sections requiring authentication carry a sign-in badge.
  \item \textbf{Login and Registration} — Authentication screens for account creation and sign-in, with client-side validation and inline error feedback.
  \item \textbf{Admin dashboard} — Statistics cards (active offers, registered users, scrape sessions, scrape success rate), operator health panel, per-family plan breakdown, detailed scrape history log, and a notifications tab for system events.
\end{enumerate}

\section{Justification of the Technology Choices}

Two principles guided every choice in the technology stack: keep the front-end and the back-end in a single project so that type definitions travel through every layer without manual synchronisation, and select the lightest tool that fully solves the problem rather than the most fashionable one. Table~\ref{tab:tech-choices} consolidates each retained tool together with the alternatives that were genuinely considered and the reasons that decided the choice. Two cross-references point to chapters where the depth is greatest: the browser-automation row refers to Chapter~1 §1.3, where the full scraping-tool landscape is evaluated; the database row refers to the load-test results in Chapter~4 §4.3, which anchor the SQLite choice empirically.

\begin{table}[H]
  \caption{Technology stack --- chosen tool, considered alternatives, and reasons for selection}
  \label{tab:tech-choices}
  \centering\footnotesize
  \begin{tabular}{|p{2.3cm}|p{2.0cm}|p{2.6cm}|p{7.2cm}|}
    \hline
    \textbf{Component} & \textbf{Chosen} & \textbf{Alternatives considered} & \textbf{Reasons for selection} \\
    \hline
    Full-stack framework & Next.js 16 & Nuxt (Vue), SvelteKit, Express + React separated &
    Single project for both front-end (React server components in \texttt{page.tsx}) and back-end (\texttt{route.ts} handlers); App Router file-system routing; native server-side rendering and incremental static regeneration; TypeScript types flow from Prisma through API handlers into React components without manual export. Nuxt and SvelteKit are comparable on features but offer smaller ecosystems for the specific authentication and ORM libraries required \parencite{NextJSDocs2024}. \\
    \hline
    ORM & Prisma 7 & TypeORM, Drizzle, raw SQL &
    The single \texttt{schema.prisma} file is the unique source of truth for the data model: types are auto-generated, migrations are derived mechanically, and any column change propagates at compile time. Prisma~7's driver-adapter system gives a clean migration path to PostgreSQL by swapping the adapter alone. Raw SQL forces duplicate type definitions in two places with no static sync guarantee; TypeORM and Drizzle keep declarations inside application code rather than in a dedicated schema file \parencite{PrismaDocs2024}. \\
    \hline
    Database & SQLite & PostgreSQL, MySQL &
    The most-deployed database engine in the world; embedded in every smartphone and modern browser \parencite{Mitchell2018}. Load tests (Ch4 §4.3) sustain 215~req/s on the offers endpoint with zero errors at fifty concurrent connections; the recommendation endpoint hits its CPU-bound ceiling of 60~req/s before the database becomes a bottleneck. PostgreSQL or MySQL would add a daemon, credentials, and a non-trivial deployment footprint for no measurable benefit at the project's scale. \\
    \hline
    Authentication & NextAuth.js v5 & Custom JWT, Passport.js, Clerk, Auth0 &
    Purpose-built for Next.js: JWT sessions out of the box, native Prisma-adapter integration, fully self-hosted in the project repository. Custom JWT rejected because authentication is too security-critical to write from scratch. Passport.js abstractions assume a separate back-end and contradict the unified Next.js model. Clerk and Auth0 introduce a recurring fee plus a transfer of user data to a third-party identity store, which is incompatible with an academic deliverable. \\
    \hline
    Browser automation & Playwright (headless Microsoft Edge) & Puppeteer, Selenium, plain HTTP, Scrapy, crawlee, OCR, paid scraping APIs &
    A real-browser fingerprint defeats operator anti-bot layers that reject plain HTTP. Spaced retries (0\,s, 7\,s, 18\,s) and a per-operator circuit breaker ride out intermittent operator-server resets. Full alternatives evaluation in Chapter~1 §1.3. \\
    \hline
    Language & TypeScript & JavaScript &
    Compile-time type safety across 8 entities and 11 API routes; editor-level refactoring catches schema-drift errors before run-time; types travel through Prisma, API handlers, and React components without manual export. \\
    \hline
    Unit testing & Vitest & Jest, Mocha + Chai &
    Native ESM and TypeScript support without an additional Babel pipeline; configuration shared with the project's Vite build; the 99-test suite completes in approximately two seconds. \\
    \hline
    Styling & CSS custom properties & Tailwind CSS, CSS Modules &
    Operator-coloured theming via inheritance from a single \texttt{--accent} variable per card; the comparison columns are tinted to match. Tailwind would require dynamic class composition or arbitrary-value classes that defeat its design-system purpose; CSS Modules introduce build-time class-name mangling that does not coexist gracefully with Next.js server components. \\
    \hline
    Animations & Framer Motion & React Spring, plain CSS keyframes &
    Declarative \texttt{motion.*} props integrate with React component lifecycles; physics-based defaults match the visual polish of the operator brand pages and require considerably less effort than hand-written keyframes for equivalent quality. \\
    \hline
  \end{tabular}
\end{table}

Every row above represents a deliberate decision rather than a default, and each is anchored either by measured evidence (load-test numbers for SQLite, test-suite duration for Vitest) or by a structural argument that ties the tool to a specific requirement of the project (operator anti-bot for Playwright, schema as single source of truth for Prisma, security surface for NextAuth.js). The cross-reference pattern --- consolidated reasoning here, depth deferred to the corresponding chapter --- keeps this section dense and scannable without losing analytical content.
