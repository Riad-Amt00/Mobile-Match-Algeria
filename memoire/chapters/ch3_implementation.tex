\chapter{System Implementation}

The architectural and design decisions documented in Chapter~2, the three tier architecture, the data model, the API route map, the tiered ranking recommendation engine, and the technology stack with Next.js, Prisma, SQLite, Playwright and NextAuth, now have to be turned into running code. The present chapter walks through that realisation subsystem by subsystem, in roughly the order in which a request travels through the system. Section~3.1 establishes the development environment that supports every later choice. Sections~3.2--3.3 describe the data layer: the automated scraping pipeline that feeds the catalogue and the REST API that exposes it. Section~3.4 documents the recommendation engine introduced conceptually in Chapter~1 §1.3.2, with its full algorithm and its iterative design history. Sections~3.5--3.8 cover the four user facing features defined in the subject fiche: structured search, comparative visualisation, savings calculator, and the split stream notification system. Section~3.9 illustrates the nine key user interface screens; sections~3.10--3.11 close with the security architecture and the deployment configuration. The chapter is dense with concrete artefacts (algorithm diagrams, route maps, screenshots) because the goal is to show that every Chapter~2 design choice has a corresponding piece of working code.

\section{Data Aggregation Module}

\subsection{Scraper Architecture}

The data aggregation module resides in \textit{src/lib/scraper/} and follows a strict separation of concerns. Three per operator scrapers (\textit{djezzy.ts}, \textit{ooredoo.ts}, \textit{mobilis.ts}) are each responsible only for fetching and parsing their respective operator's plan page and returning a normalised array of raw offer objects. A central orchestrator (\textit{index.ts}) coordinates all three scrapers and handles every database operation, deactivation decision, and notification dispatch. A shared validation module (\textit{validate.ts}) provides robust parsers for the recurring formats encountered on the operator websites: prices in Algerian Dinars (\guillemotleft{}DA\guillemotright{}), data volumes in gigabytes (\guillemotleft{}Go\guillemotright{}, \guillemotleft{}GB\guillemotright{}), and validity periods (\guillemotleft{}jours\guillemotright{}, \guillemotleft{}semaines\guillemotright{}, \guillemotleft{}mois\guillemotright{}). A browser backed fetcher (\textit{fetch.ts}) launches a real headless instance of Microsoft Edge via Playwright (falling back to Playwright's bundled Chromium when Edge is unavailable), retries each URL up to three times with spaced delays of zero, seven, and eighteen seconds, and opens a per operator circuit breaker after repeated failures to switch the affected operator to its verified fallback dataset.

\subsection{Scraping Algorithm}

Table~\ref{tab:scraper-algo} presents the algorithm executed by the orchestrator for a single operator (input: \texttt{operator}, \texttt{scraper\_fn}; output: \texttt{ScrapeResult}).

\begin{table}[H]
  \caption{Algorithm of the automated scraping pipeline}
  \label{tab:scraper-algo}
  \centering\small
  \begin{tabular}{|p{0.8cm}|p{12.5cm}|}
    \hline
    \textbf{Step} & \textbf{Action} \\
    \hline

  \end{tabular}
\end{table}

A key precision mechanism is the \textbf{per family deactivation} at step~5. Rather than comparing global offer counts, which would incorrectly block cleanup when the total scrape count differs from the database total due to unrelated family changes, the orchestrator groups the scraped offers by their source URL. Each URL corresponds to exactly one plan family (for example, one page for LEGEND, one for CAMPUCE, one for DjezzyNet). For each family that returned at least one offer in the current run, any database record sharing that source URL but absent from the current scrape is marked inactive. This detects removed plans precisely at the family level, independently of what other families returned in the same run.

\subsection{Normalisation, Validation, and Scheduled Automation}

Each operator presents plan data in a different format, so a normalisation pipeline applies the following transformations before any record is stored: data volumes in megabytes are converted to gigabytes; plan names are trimmed and stripped of promotional suffixes; missing voice or SMS values default to zero; unlimited values are stored as the sentinel \texttt{-1}; the plan type (prepaid, postpaid, data only) is inferred from page context when not explicit; and a unique slug is generated from the normalised name. The pipeline outputs objects conforming to the \texttt{Offer} schema. The scrapers are accompanied by a snapshot based test suite under \textit{src/lib/scraper/\_\_tests\_\_}, one parser level test per operator (Djezzy CAMPUCE, Djezzy LEGEND, Ooredoo~500, Ooredoo~POP, Mobilis Pass Internet) verifies that the parser still extracts at least one offer from a frozen HTML fixture and that every extracted offer passes basic plausibility checks (no zero prices, no unrealistic data values, no \guillemotleft{}data == price\guillemotright{} parsing bugs), complemented by thirty independent tests covering multilingual unit parsing in \textit{validate.ts}. This infrastructure has caught real parser regressions, most notably an Ooredoo POP page change in which data and price values briefly appeared in the same DOM node. The orchestrator runs automatically on a scheduled basis through the Next.js instrumentation hook (administrators may also trigger a manual run from the dashboard); after each successful run it inspects every updated offer and dispatches notifications: \texttt{price\_drop} to users who saved an offer whose price decreased, \texttt{new\_offer} to every registered user when a brand new plan is inserted, and \texttt{scrape\_complete} or \texttt{scrape\_failed} to administrators only.

\subsection{Cross Operator Comparison Routing}

One non trivial design decision in the offers route concerns the comparison feature. When a user selects plans from different operators and navigates to the comparison page, the IDs are passed as a query parameter (\texttt{?ids=a,b,c}). The \textit{/api/offers} handler detects this parameter and executes a direct lookup by ID list, deliberately bypassing the \texttt{isActive} filter that applies to the normal listing path. This ensures that saved plans remain comparable even if a subsequent scrape run has marked them inactive.

\subsection{Authentication}

User authentication is implemented with NextAuth.js using the Credentials provider. Passwords are hashed with bcrypt at registration and verified at sign in. Sessions are JWT based with a thirty day expiry. The \texttt{role} field (\texttt{USER} or \texttt{ADMIN}) is embedded in the session token and verified at the start of every admin gated route handler. A one time administrator claim mechanism (\textit{/api/admin/claim}) allows a registered user to elevate their role using a server side secret defined in the \texttt{ADMIN\_CLAIM\_CODE} environment variable.

\section{Recommendation Engine}

\subsection{Two Layer Decision Model}

The recommendation engine is implemented in \textit{src/lib/recommendation.ts}. It separates the problem into two layers: a categorical \emph{filtering} layer that excludes offers incompatible with the user's hard constraints, and a \emph{ranking} layer that orders the survivors with \textbf{TOPSIS} (Technique for Order of Preference by Similarity to Ideal Solution), a standard multi criteria decision method that ranks alternatives by their Euclidean distance to an ideal and an anti ideal solution \parencite{HwangYoon1981, TaherdoostMadanchian2023}. The criterion weights that TOPSIS requires are obtained from the user's \emph{ranking} of the criteria through the rank order centroid (ROC) method \parencite{BarronBarrett1996}, so no weight is chosen by hand. Both are content based and need no interaction history, which suits the cold start setting. Every step of Table~\ref{tab:rec-algo} is a published formula; the only project specific decisions are which criteria the user may rank and that the budget is a strict ceiling.

\begin{table}[H]
  \caption{Recommendation ranking algorithm (TOPSIS with rank order centroid weights)}
  \label{tab:rec-algo}
  \centering\small
  \begin{tabular}{|p{0.8cm}|p{12.5cm}|}
    \hline
    \textbf{Step} & \textbf{Action} \\
    \hline
    1  & \textit{Filter}: discard offers failing a hard constraint, budget ceiling (\texttt{priceDA $>$ needs.budget}), preferred operator, plan type, network, or an unlimited calls / SMS toggle. \\ \hline
    2  & \textit{Weights}: turn the user's ranking of the criteria into weights by rank order centroid, $w_k = \tfrac{1}{n}\sum_{i=k}^{n}\tfrac{1}{i}$ (default criteria: price, data; two criteria give $0.75$ and $0.25$). \\ \hline
    3  & \textit{Normalise and weight}: $r_{ij} = x_{ij}/\sqrt{\sum_i x_{ij}^2}$, then $v_{ij} = w_j\, r_{ij}$. \\ \hline
    4  & \textit{Ideal / anti ideal}: $A^{+}_j$ and $A^{-}_j$ are the best and worst weighted value in column $j$ (minimum for the cost criterion price, maximum for benefit criteria such as data). \\ \hline
    5  & \textit{Distances and closeness}: $S_i^{\pm} = \sqrt{\sum_j (v_{ij}-A^{\pm}_j)^2}$, then $C_i = S_i^{-}/(S_i^{+}+S_i^{-}) \in [0,1]$. \\ \hline
    6  & Rank by $C_i$ (descending), return the top $N$ with \texttt{matchReasons[~]}; $C_i$ is reported as the match score. \\ \hline
  \end{tabular}
\end{table}

\subsection{Hard Filters and TOPSIS Ranking}

The hard filter layer treats every categorical preference as a binary go / no go condition rather than a scoring contribution: any offer that fails a constraint is discarded outright. This is the \emph{conjunctive (constraint) method}, the non compensatory screening step of multi attribute decision making \parencite{HwangYoon1981}, in which an alternative must satisfy every minimum requirement to remain eligible. Table~\ref{tab:hard-filters} lists the four constraint categories applied at this layer. The continuous trade offs (price, data) are deliberately excluded from this layer because they belong to the ranking stage.

\begin{table}[H]
  \caption{Hard filter constraints applied at the categorical layer}
  \label{tab:hard-filters}
  \centering\small
  \begin{tabular}{|p{3.0cm}|p{10.3cm}|}
    \hline
    \textbf{Constraint} & \textbf{Rule} \\ \hline
    Budget ceiling & Discard offers where \texttt{priceDA $>$ needs.budget}. \\ \hline
    Operator       & If a preferred operator is set ($\neq$ \guillemotleft{}any\guillemotright{}), keep only its offers. \\ \hline
    Plan type, network & Keep only offers matching the requested type (prepaid / postpaid / data only) and network generation (4G / 5G). \\ \hline
    Calls and SMS  & If the \guillemotleft{}unlimited\guillemotright{} toggle is set, keep only offers with the corresponding unlimited sentinel (\texttt{-1}). \\ \hline
  \end{tabular}
\end{table}

The ranking layer asks the user only to \emph{rank} the criteria (price, data) rather than to assign numeric weights, a known difficulty since users have well defined preferences but cannot accurately quantify the corresponding weights \parencite{BarronBarrett1996}; rank order centroid supplies the weights from that ranking. The match score reported to the user is the TOPSIS closeness coefficient $C_i \in [0,1]$, scaled to a percentage, so no separate scoring formula is introduced. Only two modelling choices remain the project's own, summarised in Table~\ref{tab:rec-params}.

\begin{table}[H]
  \caption{Project specific modelling choices in the ranking layer}
  \label{tab:rec-params}
  \centering\small
  \begin{tabular}{|p{3.4cm}|p{9.9cm}|}
    \hline
    \textbf{Choice} & \textbf{Rationale} \\ \hline
    Rankable criteria: price (cost) and data (benefit) & The two attributes consumers trade off most; voice, SMS, and network are available as further ranked criteria for the daily batch job. The budget is handled as a hard ceiling rather than a ranked criterion. \\ \hline
    Weights derived from the ranking (ROC), not entered by hand & Users can order their priorities but not quantify them; rank order centroid is the most accurate of the simple rank based weighting formulae \parencite{BarronBarrett1996}, so the weights are derived rather than invented. \\ \hline
  \end{tabular}
\end{table}

\subsection{Method Selection}

TOPSIS was selected after comparing the candidate multi criteria methods against the project's constraints: a cold start with no interaction history, a user who can \emph{rank} but not \emph{weight} criteria, and the need for a bounded match score. Table~\ref{tab:rec-history} summarises the comparison.

\begin{table}[H]
  \caption{Candidate ranking methods and the selection of TOPSIS}
  \label{tab:rec-history}
  \centering\small
  \begin{tabular}{|p{4.4cm}|p{9.0cm}|}
    \hline
    \textbf{Method} & \textbf{Verdict for this project} \\ \hline
    Collaborative filtering / deep learning recommenders & Rejected: require an interaction history that is absent at launch (cold start) \parencite{AdomaviciusTuzhilin2005, ZhangColdStart2025}. \\ \hline
    Simple additive weighting (weighted sum) & Considered: simple, but the score is unbounded and sensitive to how the raw scales are combined, and it still needs weights. \\ \hline
    Lexicographic / strictly non compensatory ordering & Considered \parencite{Fishburn1974, Roberts1979}: follows the top priority absolutely, but a negligible price gap then erases any data advantage, too rigid for choosing a consumer plan. \\ \hline
    Analytic hierarchy process (AHP) & Rejected: requires many pairwise comparisons and a consistency check that ordinary users cannot reliably provide. \\ \hline
    \textbf{TOPSIS + rank order centroid (retained)} & Chosen \parencite{HwangYoon1981, BarronBarrett1996, TaherdoostMadanchian2023}: content based (cold start safe), criteria trade off smoothly while the ROC weights still encode the user's ranking, every step is a published formula, and the closeness coefficient is a bounded match score. \\ \hline
  \end{tabular}
\end{table}

As a worked example, take a user with budget 2\,000~DA who ranks price first then data, and three in budget plans: $A$ (1\,000~DA, 8~GB), $B$ (1\,100~DA, 15~GB), and $C$ (600~DA, 4~GB). Rank order centroid gives weights $0.75$ (price) and $0.25$ (data). After vector normalisation and weighting, TOPSIS computes each plan's Euclidean distance to the ideal (cheapest, most data) and to the anti ideal, yielding closeness coefficients $C_C \approx 0.60$, $C_B \approx 0.40$, $C_A \approx 0.26$. The ranking is therefore $C, B, A$: the low price of $C$ dominates under the $0.75$ price weight, while $B$ outranks $A$ on data. Ranking data first instead would raise the weight on data and move the higher data plan $B$ up, which is exactly how the ROC weights steer the trade off.

The engine is called from two distinct contexts: the \textit{/api/recommendations} route handler executes the algorithm synchronously in response to an explicit user request (rate limited at sixty requests per minute per IP), and the scraper orchestrator runs it in batch after each successful scrape cycle to dispatch personalised \texttt{recommendation} notifications when a user's top match has changed. The engine covers the case where the user has filled out a profile and wants the system to choose for them; the complementary case, the user has a query in mind and wants the catalogue filtered by it, is handled by the structured search interface described next.

\section{Structured Search Engine}

The search engine is a parser implemented twice in symmetry: the server side parser lives inside the \texttt{GET /api/offers} handler and converts a free text query into a Prisma \texttt{where} clause, while the client side parser (\textit{src/lib/search-tokens.ts}) applies the same regular expression vocabulary to produce visible \guillemotleft{}Read as\guillemotright{} chips that show the user how the query was interpreted. Six token kinds are recognised; Table~\ref{tab:search-tokens} lists each token with its example input and resulting filter.

\begin{table}[H]
  \caption{Token kinds recognised by the search parser}
  \label{tab:search-tokens}
  \centering\small
  \begin{tabular}{|p{2.5cm}|p{4.5cm}|p{6.4cm}|}
    \hline
    \textbf{Token kind} & \textbf{Example input} & \textbf{Resulting filter} \\
    \hline
    Data volume        & \texttt{5gb}, \texttt{10 go}, \texttt{2 giga}                            & \texttt{dataGB} between $0.7\times$ and $3\times$ the stated value, or unlimited (\texttt{-1}) \\
    \hline
    Price              & \texttt{1000 da}, \texttt{500 dinars}                                    & \texttt{priceDA} within $\pm 30\,\%$ of the stated value \\
    \hline
    Network            & \texttt{4g}, \texttt{5g}, \texttt{3g}                                    & Exact substring match on the \texttt{network} column \\
    \hline
    Unlimited keyword  & \texttt{unlimited}, \texttt{illimité}, \texttt{infini}                   & Calls, SMS, or feature list contains an unlimited indicator \\
    \hline
    Operator           & \texttt{djezzy}, \texttt{ooredoo}, \texttt{mobilis}                      & Operator slug match \\

    \hline
  \end{tabular}
\end{table}

Each recognised token is consumed from the input string; the remaining words (at least two characters each) are passed through a small French to English alias table (\texttt{appel} $\rightarrow$ \texttt{call}, \texttt{données} $\rightarrow$ \texttt{data}, etc.) and then queried against a SQLite FTS5 full text index built over the offer's \texttt{name}, \texttt{features}, and operator name columns. SQLite's FTS5 module is a built in extension that ships with the database file and provides BM25 relevance ranking, prefix matching (so typing \guillemotleft{}djez\guillemotright{} matches \guillemotleft{}Djezzy\guillemotright{}), and Unicode aware tokenisation with diacritic folding (so \guillemotleft{}illimite\guillemotright{} matches \guillemotleft{}illimité\guillemotright{}), the same retrieval primitives an industrial engine would offer, obtained without any additional process or external service \parencite{SQLiteFTS5}. The index is contentless and lives in the same \textit{prisma/dev.db} file as the rest of the schema; it is rebuilt at server startup and at the end of every successful scrape run, so consistency with the canonical \texttt{Offer} table is guaranteed without incremental triggers. All structured tokens and the FTS5 result set are combined under \texttt{AND}, so the query \guillemotleft{}5\,gb djezzy\guillemotright{} returns offers covering approximately 5\,GB \emph{and} sold by Djezzy. Two assistance elements are visible on the offers page: \textbf{example chips} above the input (clickable presets such as \guillemotleft{}5 Go Djezzy\guillemotright{} or \guillemotleft{}Illimité 1000 DA\guillemotright{}), shown only when the input is empty, and a \textbf{\guillemotleft{}?\guillemotright{} help popover} next to the input which opens a syntax cheat sheet listing every recognisable token kind with an example.

\section{Comparative Visualisation and Savings Calculator}

Two short user facing features sit on top of the same recommendation backbone introduced above.

\paragraph{Comparative bar charts.} The comparison page renders, in addition to the side by side specification table, two per metric bar charts comparing the selected plans on price (lower is better) and data volume (higher is better, with the sentinel value $-1$ shown as \guillemotleft{}$\infty$\guillemotright{}). When the comparison is launched from the recommendations page, a third bar chart labelled \guillemotleft{}Annual savings\guillemotright{} is added: it shows, for each compared plan, $\max(0,\,(\mathrm{budget} - \mathrm{price}) \times 12)$ where \texttt{budget} is read from the authenticated user's saved profile, so every bar carries a real value rather than the priciest plan being pinned to zero. Each plan's bar is coloured according to its operator using the palette defined in \textit{src/lib/utils.ts}, and the corresponding columns of the table are tinted to match. The charts use the \texttt{recharts} library and are rendered client side.

\paragraph{Savings calculator.} The FICHE deliverable \guillemotleft{}calculateur d'économies potentielles\guillemotright{} is implemented as an integrated indicator on each recommendation card rather than as a standalone page, because the recommendation flow already gathers every input the calculation requires: the user's monthly budget, the data need, and the binary calls and SMS preferences. For every ranked plan whose price is below the user's monthly budget, the card displays the monthly saving (\texttt{budget} $-$ \texttt{offer.priceDA}), the annual saving (monthly saving~$\times$~12) and the percentage reduction relative to the budget. The indicator is rendered as a tinted panel below the match reasons block and is hidden when the user's budget is already at or below the plan's price, avoiding misleading zero or negative savings values. The user can then launch a side by side comparison of the top three plans, where the same budget relative annual saving is rendered as the third bar chart described above. Folding the calculation into the recommendation card removes a redundant entry point while preserving the deliverable's behaviour and three component output.

The two stream separation is enforced at the source: every notification dispatch function in the scraper orchestrator (\texttt{notifyUsers}, \texttt{notifyAdmins}, \texttt{notifyAdminsFailure}) filters the recipient set by the \texttt{User.role} field before writing any row. Each notification type also drives the click through routing applied by the navbar bell and the admin panel: user stream notifications navigate to the offer detail page or to \textit{/recommend} depending on the type, while administrator stream notifications navigate to \textit{/admin?tab=history}.

The separation was introduced specifically to fix two defects in an earlier single stream design. Without role filters on the dispatch functions, an administrator's feed was systematically polluted with consumer facing alerts produced for every newly scraped offer. More damagingly, both administrator \guillemotleft{}scrape complete\guillemotright{} and user \guillemotleft{}new offer\guillemotright{} events used the same \texttt{type} value, so a non administrator user clicking on a \guillemotleft{}new offer\guillemotright{} notification was routed to \textit{/admin?tab=history}, a page they were not permitted to access. The current two stream design, role filtered dispatch, distinct \texttt{type} values, and type aware routing, eliminates both defects by construction.

The scenario exercises every defensive property of the two stream design at once: row 3 is admin only because the role filter excludes \texttt{USER} role recipients; rows 4--6 are user only because the dispatch functions for those types restrict the recipient query to \texttt{role = 'USER'}; row 5 narrows further by joining against \texttt{SavedOffer.userId} so only users who had actually saved the affected plan receive the alert; and row 6 narrows further still by requiring a saved \texttt{UserProfile}. The click through routing in row 9 reads the \texttt{type} field of the clicked notification and dispatches accordingly, an administrator clicking the \texttt{scrape\_complete} row never lands on a user facing page, and a user clicking the \texttt{new\_offer} row never lands on the admin page.

Table~\ref{tab:security} summarises the security mechanisms applied across the application together with the class of threat each mechanism addresses and its concrete implementation in the codebase.

    \hline

\section{Deployment}

{\sloppy The application is built for production with \texttt{next build}, which performs static analysis, tree shaking, and route level code splitting. The resulting artefact is a Node.js server launched with \texttt{next start}. Three environment variables must be set: \texttt{DATABASE\_URL} (path to the SQLite file), \texttt{NEXTAUTH\_SECRET} (JWT signing key), and \texttt{NEXTAUTH\_URL} (base URL). The SQLite file is the only persistent artefact that must be preserved across deployments. The current evaluation deployment runs in production mode on a single machine; public deployment to a managed cloud host is identified as a perspective in the general conclusion.\par}
