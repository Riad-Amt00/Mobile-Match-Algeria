\chapter{System Implementation}

The architectural and design decisions documented in Chapter~2 --- the three-tier architecture, the data model, the API route map, the tiered-ranking recommendation engine, and the technology stack with Next.js, Prisma, SQLite, Playwright and NextAuth --- now have to be turned into running code. The present chapter walks through that realisation subsystem by subsystem, in roughly the order in which a request travels through the system. Section~3.1 establishes the development environment that supports every later choice. Sections~3.2--3.3 describe the data layer: the automated scraping pipeline that feeds the catalogue and the REST API that exposes it. Section~3.4 documents the recommendation engine introduced conceptually in Chapter~1 §1.3.2, with its full algorithm and its iterative-design history. Sections~3.5--3.8 cover the four user-facing features defined in the subject fiche: structured search, comparative visualisation, savings calculator, and the split-stream notification system. Section~3.9 illustrates the nine key user-interface screens; sections~3.10--3.11 close with the security architecture and the deployment configuration. The chapter is dense with concrete artefacts (algorithm diagrams, route maps, screenshots) because the goal is to show that every Chapter~2 design choice has a corresponding piece of working code.

\section{Data Aggregation Module}

\subsection{Scraper Architecture}

The data-aggregation module resides in \texttt{src/lib/scraper/} and follows a strict separation of concerns. Three per-operator scrapers (\texttt{djezzy.ts}, \texttt{ooredoo.ts}, \texttt{mobilis.ts}) are each responsible only for fetching and parsing their respective operator's plan page and returning a normalised array of raw offer objects. A central orchestrator (\texttt{index.ts}) coordinates all three scrapers and handles every database operation, deactivation decision, and notification dispatch. A shared validation module (\texttt{validate.ts}) provides robust parsers for the recurring formats encountered on the operator websites: prices in Algerian Dinars (\guillemotleft{}DA\guillemotright{}), data volumes in gigabytes (\guillemotleft{}Go\guillemotright{}, \guillemotleft{}GB\guillemotright{}), and validity periods (\guillemotleft{}jours\guillemotright{}, \guillemotleft{}semaines\guillemotright{}, \guillemotleft{}mois\guillemotright{}). A browser-backed fetcher (\texttt{fetch.ts}) launches a real headless instance of Microsoft Edge via Playwright (falling back to Playwright's bundled Chromium when Edge is unavailable), retries each URL up to three times with spaced delays of zero, seven, and eighteen seconds, and opens a per-operator circuit breaker after repeated failures to switch the affected operator to its verified fallback dataset.

\subsection{Scraping Algorithm}

Table~\ref{tab:scraper-algo} presents the algorithm executed by the orchestrator for a single operator (input: \textit{operator}, \textit{scraper\_fn}; output: \textit{ScrapeResult}).

\begin{table}[H]
  \caption{Algorithm of the automated scraping pipeline}
  \label{tab:scraper-algo}
  \centering\small
  \begin{tabular}{|p{0.8cm}|p{12.5cm}|}
    \hline
    \textbf{Step} & \textbf{Action} \\
    \hline
    1   & Record \textit{startedAt}; create ScrapeLog with status = RUNNING. \\ \hline
    2   & Invoke \textit{scraper\_fn}: fetch the operator page through a real headless Edge browser (spaced retries + circuit breaker), parse HTML with Cheerio, normalise attributes via \texttt{validate.ts}. \\ \hline
    3   & Filter out offers missing all data, voice, and SMS values. \\ \hline
    4a  & For each valid offer, compute \texttt{slug = slugify(offer.name)}. \\ \hline
    4b  & If the slug exists in DB $\Rightarrow$ UPDATE record (insert \texttt{PriceHistory} if \texttt{priceDA} changed); else $\Rightarrow$ INSERT and notify users. \\ \hline
    5   & Per-family deactivation: group scraped offers by source URL (one URL~=~one plan family); for each non-empty family, set \texttt{isActive=false} for DB offers of that URL absent from the scrape. \\ \hline
    6   & Update ScrapeLog: status = SUCCESS, duration, \texttt{offersAdded}, \texttt{offersUpdated}, \texttt{offersDeactivated}. \\ \hline
    7   & Return ScrapeResult. \emph{On error: status = FAILED, log \texttt{errorMessage}.} \\ \hline
  \end{tabular}
\end{table}

A key precision mechanism is the \textbf{per-family deactivation} at step~5. Rather than comparing global offer counts — which would incorrectly block cleanup when the total scrape count differs from the database total due to unrelated family changes — the orchestrator groups the scraped offers by their source URL. Each URL corresponds to exactly one plan family (for example, one page for LEGEND, one for CAMPUCE, one for DjezzyNet). For each family that returned at least one offer in the current run, any database record sharing that source URL but absent from the current scrape is marked inactive. This detects removed plans precisely at the family level, independently of what other families returned in the same run.

\subsection{Normalisation, Validation, and Scheduled Automation}

Each operator presents plan data in a different format, so a normalisation pipeline applies the following transformations before any record is stored: data volumes in megabytes are converted to gigabytes; plan names are trimmed and stripped of promotional suffixes; missing voice or SMS values default to zero; unlimited values are stored as the sentinel \texttt{-1}; the plan type (prepaid, postpaid, data-only) is inferred from page context when not explicit; and a unique slug is generated from the normalised name. The pipeline outputs objects conforming to the \texttt{Offer} schema. The scrapers are accompanied by a snapshot-based test suite under \texttt{src/lib/scraper/\_\_tests\_\_} --- one parser-level test per operator (Djezzy CAMPUCE, Djezzy LEGEND, Ooredoo~500, Ooredoo~POP, Mobilis Pass Internet) verifies that the parser still extracts at least one offer from a frozen HTML fixture and that every extracted offer passes basic plausibility checks (no zero prices, no unrealistic data values, no \guillemotleft{}data == price\guillemotright{} parsing bugs) --- complemented by thirty independent tests covering multilingual unit parsing in \texttt{validate.ts}. This infrastructure has caught real parser regressions, most notably an Ooredoo POP page change in which data and price values briefly appeared in the same DOM node. The orchestrator runs automatically on a scheduled basis through the Next.js instrumentation hook (administrators may also trigger a manual run from the dashboard); after each successful run it inspects every updated offer and dispatches notifications: \texttt{price\_drop} to users who saved an offer whose price decreased, \texttt{new\_offer} to every registered user when a brand-new plan is inserted, and \texttt{scrape\_complete} or \texttt{scrape\_failed} to administrators only.

\subsection{Cross-Operator Comparison Routing}

One non-trivial design decision in the offers route concerns the comparison feature. When a user selects plans from different operators and navigates to the comparison page, the IDs are passed as a query parameter (\texttt{?ids=a,b,c}). The \texttt{/api/offers} handler detects this parameter and executes a direct lookup by ID list, deliberately bypassing the \texttt{isActive} filter that applies to the normal listing path. This ensures that saved plans remain comparable even if a subsequent scrape run has marked them inactive.

\subsection{Authentication}

User authentication is implemented with \textit{NextAuth.js} using the Credentials provider. Passwords are hashed with bcrypt at registration and verified at sign-in. Sessions are JWT-based with a thirty-day expiry. The \texttt{role} field (\texttt{USER} or \texttt{ADMIN}) is embedded in the session token and verified at the start of every admin-gated route handler. A one-time administrator-claim mechanism (\texttt{/api/admin/claim}) allows a registered user to elevate their role using a server-side secret defined in the \texttt{ADMIN\_CLAIM\_CODE} environment variable.

\section{Recommendation Engine}

\subsection{Two-Layer Decision Model}

The recommendation engine is implemented in \texttt{src/lib/recommendation.ts}. It separates the recommendation problem into two distinct layers: a categorical filtering layer that excludes offers incompatible with the user's hard constraints, and a tiered-ranking layer that orders the remaining offers according to the user's primary and secondary continuous priorities. The second layer is an applied form of \textbf{lexicographic preference ordering with bounded relaxation}, a well-established technique in multi-criteria decision making \parencite{Fishburn1974, Roberts1979}: the contribution of this work is the adaptation of that technique to a cold-start consumer-plan context, not the algorithm itself. The final defensible design (Table~\ref{tab:rec-algo}) was reached after several rejected attempts (Section~3.4.3), each of which exposed a specific failure mode of the previous one.

\begin{table}[H]
  \caption{Tiered-ranking recommendation algorithm}
  \label{tab:rec-algo}
  \centering\small
  \begin{tabular}{|p{0.8cm}|p{12.5cm}|}
    \hline
    \textbf{Step} & \textbf{Action} \\
    \hline
    1a  & \textit{Budget ceiling}: discard offers where \texttt{priceDA $>$ needs.budget}. \\ \hline
    1b  & \textit{Operator}: discard offers whose operator does not match the user's preference (if any). \\ \hline
    1c  & \textit{Plan type, network, calls, SMS}: discard offers that do not satisfy the user's categorical preferences. \\ \hline
    2a  & Compute the price merit $m_1 = \mathrm{clamp01}(\mathrm{priceDA} / \mathrm{needs.budget})$ --- closeness to target price. \\ \hline
    2b  & Compute the data merit $m_2 = \mathrm{clamp01}(\mathrm{dataGB} / \mathrm{needs.dataGB})$ --- coverage of declared need. \\ \hline
    3a  & Tier ($P_1$ = primary priority): $\mathrm{tier} = \mathrm{round}(m_{P_1} \times 4) / 4 \in \{0,\,0.25,\,0.5,\,0.75,\,1\}$. \\ \hline
    3b  & Composite key ($P_2$ = secondary): $C = \mathrm{tier} + 0.24 \times m_{P_2}$ (within-tier term $<0.25$, never crosses a tier boundary). \\ \hline
    4   & Sort by composite key; ties broken by the base fitness score. \\ \hline
    5   & Diversity rule: if the top three are from a single operator and the next operator's best result is $\geq 85\,\%$ of the third's composite, swap it in. \\ \hline
    6   & Return the top-$N$ results with \texttt{matchReasons[~]}. \\ \hline
  \end{tabular}
\end{table}

\subsection{Hard Filters and Tiered Ranking}

The hard-filter layer treats every categorical preference as a binary go / no-go condition rather than a scoring contribution: any offer that fails a constraint is discarded outright. Table~\ref{tab:hard-filters} lists the four constraint categories applied at this layer. The continuous trade-offs (price, data) are deliberately excluded from this layer because they belong to the ranking stage.

\begin{table}[H]
  \caption{Hard-filter constraints applied at the categorical layer}
  \label{tab:hard-filters}
  \centering\small
  \begin{tabular}{|p{3.0cm}|p{10.3cm}|}
    \hline
    \textbf{Constraint} & \textbf{Rule} \\ \hline
    Budget ceiling & Discard offers where \texttt{priceDA $>$ needs.budget}. \\ \hline
    Operator       & If a preferred operator is set ($\neq$ \guillemotleft{}any\guillemotright{}), keep only its offers. \\ \hline
    Plan type, network & Keep only offers matching the requested type (prepaid / postpaid / data-only) and network generation (4G / 5G). \\ \hline
    Calls and SMS  & If the \guillemotleft{}unlimited\guillemotright{} toggle is set, keep only offers with the corresponding unlimited sentinel (\texttt{-1}). \\ \hline
  \end{tabular}
\end{table}

The ranking layer then asks the user to rank two criteria from the set \{price, data\} rather than to assign numeric weights, a known difficulty in multi-criteria decision contexts where users have well-defined preferences but cannot accurately quantify the corresponding weights \parencite{Roberts1979}. Each rankable criterion is scored as a need-relative ratio rather than a pool-normalised one, so a catalogue outlier (a 10~DA plan with no data) cannot distort the ranking for users with a typical budget. The two key parameters of the algorithm and their justifications are summarised in Table~\ref{tab:rec-params}.

\begin{table}[H]
  \caption{Justification of the key parameters of the tiered-ranking layer}
  \label{tab:rec-params}
  \centering\small
  \begin{tabular}{|p{3.0cm}|p{10.3cm}|}
    \hline
    \textbf{Parameter} & \textbf{Why this value} \\ \hline
    Five tier centres ($h = 0.25$) & A smaller catalogue (~100 plans) does not statistically support finer partitioning; a larger number of tiers would shrink each tier toward a single offer and defeat the within-tier ordering. \\ \hline
    Secondary multiplier $= 0.24$ & Strictly below the tier width $h = 0.25$: guarantees that no within-tier improvement on the secondary criterion can lift an offer past a higher tier; the $0.01$ safety margin absorbs floating-point rounding. \\ \hline
  \end{tabular}
\end{table}

\subsection{Iterative Design History}

The tiered model was reached only after four earlier designs were rejected, each exposing a specific failure mode of the previous one. Table~\ref{tab:rec-history} summarises the five iterations.

\begin{table}[H]
  \caption{Iterative design history of the recommendation engine}
  \label{tab:rec-history}
  \centering\small
  \begin{tabular}{|p{0.6cm}|p{4.5cm}|p{8.5cm}|}
    \hline
    \textbf{\#} & \textbf{Design} & \textbf{Why rejected} \\ \hline
    1 & Flat bonus ($+12/+8/+4$) on a 100-pt fitness score & Bonus too small to overcome the base score; recommendations always followed price regardless of user choice. \\ \hline
    2 & Weighted sum of merits ($0.6, 0.4$) & A great score on one criterion compensated for a poor score on the other, contradicting the user's stated priority. \\ \hline
    3 & Weighted geometric mean & Tuning the weights merely shifted the symptom between \guillemotleft{}follows only price\guillemotright{} and \guillemotleft{}follows only data\guillemotright{} without ever producing a clean primary-then-secondary order. \\ \hline
    4 & Tiered ranking with tier step $h = 0.1$ & Cheapest tier so narrow it contained only micro-plans, producing degenerate results. \\ \hline
    5 & \textbf{Tiered ranking, $h = 0.25$, secondary multiplier $0.24$ (retained)} & Reliably produces \guillemotleft{}follow the first priority, then get as close as possible to the second\guillemotright{}, matching the user's mental model. \\ \hline
  \end{tabular}
\end{table}

To illustrate the rejection of design~3 concretely, consider a user with budget 1\,400~DA, data need 20~GB, priorities \texttt{[price, data]}, and two candidate offers $O_A$ (200~DA / 3~GB) and $O_B$ (1\,400~DA / 25~GB). The geometric-mean composite $m_1^{0.6} \cdot m_2^{0.4}$ returns $0.14$ for $O_A$ and $1.00$ for $O_B$, ranking $O_B$ first --- directly contradicting the user's stated primary preference for price. The tiered model places $O_A$ in tier $0.00$ and $O_B$ in tier $1.00$; the primary priority strictly determines the tier, so $O_A$ leads. The two models produce opposite top results from the same inputs --- which is the failure mode the iterative process was eliminating.

The engine is called from two distinct contexts: the \texttt{/api/recommendations} route handler executes the algorithm synchronously in response to an explicit user request (rate-limited at sixty requests per minute per IP), and the scraper orchestrator runs it in batch after each successful scrape cycle to dispatch personalised \texttt{recommendation} notifications when a user's top match has changed. The engine covers the case where the user has filled out a profile and wants the system to choose for them; the complementary case --- the user has a query in mind and wants the catalogue filtered by it --- is handled by the structured search interface described next.

\section{Structured Search Engine}

The search engine is a parser implemented twice in symmetry: the server-side parser lives inside the \texttt{GET /api/offers} handler and converts a free-text query into a Prisma \texttt{where} clause, while the client-side parser (\texttt{src/lib/search-tokens.ts}) applies the same regular-expression vocabulary to produce visible \guillemotleft{}Read as\guillemotright{} chips that show the user how the query was interpreted. Eight token kinds are recognised; Table~\ref{tab:search-tokens} lists each token with its example input and resulting filter.

\begin{table}[H]
  \caption{Token kinds recognised by the search parser}
  \label{tab:search-tokens}
  \centering\small
  \begin{tabular}{|p{2.5cm}|p{4.5cm}|p{6.4cm}|}
    \hline
    \textbf{Token kind} & \textbf{Example input} & \textbf{Resulting filter} \\
    \hline
    Data volume        & \texttt{5gb}, \texttt{10 go}, \texttt{2 giga}                            & \texttt{dataGB} between $0.7\times$ and $3\times$ the stated value \\

    \hline

    \hline
    Voice minutes      & \texttt{100 min}, \texttt{200 minutes}                                   & \texttt{voiceMinutes $\geq$ N} or unlimited (\texttt{-1}) \\
    \hline
    Network            & \texttt{4g}, \texttt{5g}, \texttt{3g}                                    & Exact substring match on the \texttt{network} column \\

Each recognised token is consumed from the input string; the remaining words (at least two characters each) are passed through a small French-to-English alias table (\texttt{appel} $\rightarrow$ \texttt{call}, \texttt{données} $\rightarrow$ \texttt{data}, etc.) and must appear in the offer's \texttt{name}, \texttt{features}, or operator name. All tokens are combined under \texttt{AND}, so the query \guillemotleft{}5\,gb djezzy\guillemotright{} returns offers covering approximately 5\,GB \emph{and} sold by Djezzy. Two assistance elements are visible on the offers page: \textbf{example chips} above the input (clickable presets such as \guillemotleft{}5 Go Djezzy\guillemotright{} or \guillemotleft{}Illimité 1000 DA\guillemotright{}), shown only when the input is empty, and a \textbf{\guillemotleft{}?\guillemotright{} help popover} next to the input which opens a syntax cheat-sheet listing every recognisable token kind with an example.

\section{Comparative Visualisation and Savings Calculator}

Two short user-facing features sit on top of the same recommendation backbone introduced above.

\paragraph{Comparative bar charts.} The comparison page renders, in addition to the side-by-side specification table, two per-metric bar charts comparing the selected plans on price (lower is better) and data volume (higher is better, with the sentinel value $-1$ shown as \guillemotleft{}$\infty$\guillemotright{}). When the comparison is launched from the recommendations page, a third bar chart labelled \guillemotleft{}Annual savings\guillemotright{} is added: it shows, for each compared plan, $\max(0,\,(\mathrm{budget} - \mathrm{price}) \times 12)$ where \texttt{budget} is read from the authenticated user's saved profile --- so every bar carries a real value rather than the priciest plan being pinned to zero. Each plan's bar is coloured according to its operator using the palette defined in \texttt{src/lib/utils.ts}, and the corresponding columns of the table are tinted to match. The charts use the \texttt{recharts} library and are rendered client-side.

\paragraph{Savings calculator.} The FICHE deliverable \guillemotleft{}calculateur d'économies potentielles\guillemotright{} is implemented as an integrated indicator on each recommendation card rather than as a standalone page, because the recommendation flow already gathers every input the calculation requires: the user's monthly budget, the data need, and the binary calls and SMS preferences. For every ranked plan whose price is below the user's monthly budget, the card displays the monthly saving (\texttt{budget} $-$ \texttt{offer.priceDA}), the annual saving (monthly saving~$\times$~12) and the percentage reduction relative to the budget. The indicator is rendered as a tinted panel below the match-reasons block and is hidden when the user's budget is already at or below the plan's price, avoiding misleading zero or negative savings values. The user can then launch a side-by-side comparison of the top three plans, where the same budget-relative annual saving is rendered as the third bar chart described above. Folding the calculation into the recommendation card removes a redundant entry point while preserving the deliverable's behaviour and three-component output.

\section{Notification System}

The notification system is split into two distinct streams handled by the same \texttt{Notification} table, distinguished by their \texttt{type} field. Table~\ref{tab:notif-types} enumerates every notification type together with its target audience, the event that triggers it, and the page the user is routed to when they click the notification.

\begin{table}[H]
  \caption{Notification types --- audience, trigger, and click-through routing}
  \label{tab:notif-types}
  \centering\small
  \begin{tabular}{|p{2.7cm}|p{2.4cm}|p{4.5cm}|p{3.6cm}|}
    \hline
    \textbf{Type} & \textbf{Audience} & \textbf{Trigger} & \textbf{Routes to} \\
    \hline
    \texttt{new\_offer}        & Registered users (\texttt{USER} role) & The scraper inserts a previously unknown plan & The offer detail page \\
    \hline
    \texttt{price\_drop}       & Users who have saved that offer & A scrape detects a price decrease on a saved offer & The offer detail page \\
    \hline

    \hline

    \hline
  \end{tabular}
\end{table}

The two-stream separation is enforced at the source: every notification-dispatch function in the scraper orchestrator (\texttt{notifyUsers}, \texttt{notifyAdmins}, \texttt{notifyAdminsFailure}) filters the recipient set by the \texttt{User.role} field before writing any row. Each notification type also drives the click-through routing applied by the navbar bell and the admin panel: user-stream notifications navigate to the offer detail page or to \texttt{/recommend} depending on the type, while administrator-stream notifications navigate to \texttt{/admin?tab=history}.

The separation was introduced specifically to fix two defects in an earlier single-stream design. Without role filters on the dispatch functions, an administrator's feed was systematically polluted with consumer-facing alerts produced for every newly scraped offer. More damagingly, both administrator \guillemotleft{}scrape complete\guillemotright{} and user \guillemotleft{}new offer\guillemotright{} events used the same \texttt{type} value, so a non-administrator user clicking on a \guillemotleft{}new offer\guillemotright{} notification was routed to \texttt{/admin?tab=history} --- a page they were not permitted to access. The current two-stream design --- role-filtered dispatch, distinct \texttt{type} values, and type-aware routing --- eliminates both defects by construction.

    4 & Insertion of new plan    & For each of the two new Djezzy plans, a row is inserted in \texttt{Offer}.                                     & \texttt{new\_offer}     & Bob, Carol, and every other registered user. Routes to \texttt{/offers/[id]}. \\
    \hline
    5 & Price decrease detected  & The saved Mobilis plan's \texttt{priceDA} is rewritten from 1\,500 to 1\,300~DA in the same run.               & \texttt{price\_drop}    & Bob only (because Bob is the only user who had saved that offer). Routes to \texttt{/offers/[id]}. \\
    \hline
    6 & Re-ranking pass          & The recommendation engine re-runs against every profile; Carol's previous top-matched plan is overtaken by a newer one. & \texttt{recommendation} & Carol only. Routes to \texttt{/recommend}. \\
    \hline
    7 & Notification fan-out     & Notifications are batch-inserted into the \texttt{Notification} table grouped by \texttt{userId}.              & ---                     & --- \\
    \hline
    8 & Recipient sees the bell  & Each recipient's navbar bell badge increments by the count of unread rows for their \texttt{userId}.            & ---                     & --- \\
    \hline
    9 & Recipient clicks one     & The frontend marks the row as read (PATCH \texttt{/api/notifications}) and navigates by \texttt{type}.          & ---                     & ---                                       \\
    \hline
  \end{tabular}
\end{table}

The scenario exercises every defensive property of the two-stream design at once: row 3 is admin-only because the role filter excludes \texttt{USER}-role recipients; rows 4--6 are user-only because the dispatch functions for those types restrict the recipient query to \texttt{role = 'USER'}; row 5 narrows further by joining against \texttt{SavedOffer.userId} so only users who had actually saved the affected plan receive the alert; and row 6 narrows further still by requiring a saved \texttt{UserProfile}. The click-through routing in row 9 reads the \texttt{type} field of the clicked notification and dispatches accordingly --- an administrator clicking the \texttt{scrape\_complete} row never lands on a user-facing page, and a user clicking the \texttt{new\_offer} row never lands on the admin page.

\section{Deployment}

{\sloppy The application is built for production with \texttt{next build}, which performs static analysis, tree-shaking, and route-level code splitting. The resulting artefact is a Node.js server launched with \texttt{next start}. Three environment variables must be set: \texttt{DATABASE\_URL} (path to the SQLite file), \texttt{NEXTAUTH\_SECRET} (JWT signing key), and \texttt{NEXTAUTH\_URL} (base URL). The SQLite file is the only persistent artefact that must be preserved across deployments. The current evaluation deployment runs in production mode on a single machine; public deployment to a managed cloud host is identified as a perspective in the general conclusion.\par}
