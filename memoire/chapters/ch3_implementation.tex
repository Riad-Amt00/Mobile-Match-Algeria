\chapter{System Implementation}

The architectural and design decisions documented in Chapter~2 --- the three-tier architecture, the data model, the API route map, the tiered-ranking recommendation engine, and the technology stack with Next.js, Prisma, SQLite, Playwright and NextAuth --- now have to be turned into running code. The present chapter walks through that realisation subsystem by subsystem, in roughly the order in which a request travels through the system. Section~3.1 establishes the development environment that supports every later choice. Sections~3.2--3.3 describe the data layer: the automated scraping pipeline that feeds the catalogue and the REST API that exposes it. Section~3.4 documents the recommendation engine introduced conceptually in Chapter~1 §1.4.2, with its full algorithm and its iterative-design history. Sections~3.5--3.8 cover the four user-facing features defined in the subject fiche: structured search, comparative visualisation, savings calculator, and the split-stream notification system. Section~3.9 illustrates the nine key user-interface screens; sections~3.10--3.11 close with the security architecture and the deployment configuration. The chapter is dense with concrete artefacts (algorithm diagrams, route maps, screenshots) because the goal is to show that every Chapter~2 design choice has a corresponding piece of working code.

\section{Data Aggregation Module}

\subsection{Scraper Architecture}

The data-aggregation module resides in \texttt{src/lib/scraper/} and follows a strict separation of concerns. Three per-operator scrapers (\texttt{djezzy.ts}, \texttt{ooredoo.ts}, \texttt{mobilis.ts}) are each responsible only for fetching and parsing their respective operator's plan page and returning a normalised array of raw offer objects. A central orchestrator (\texttt{index.ts}) coordinates all three scrapers and handles every database operation, deactivation decision, and notification dispatch. A shared validation module (\texttt{validate.ts}) provides robust parsers for the recurring formats encountered on the operator websites: prices in Algerian Dinars (\guillemotleft{}DA\guillemotright{}), data volumes in gigabytes (\guillemotleft{}Go\guillemotright{}, \guillemotleft{}GB\guillemotright{}), and validity periods (\guillemotleft{}jours\guillemotright{}, \guillemotleft{}semaines\guillemotright{}, \guillemotleft{}mois\guillemotright{}). A browser-backed fetcher (\texttt{fetch.ts}) launches a real headless instance of Microsoft Edge via Playwright (falling back to Playwright's bundled Chromium when Edge is unavailable), retries each URL up to three times with spaced delays of zero, seven, and eighteen seconds, and opens a per-operator circuit breaker after repeated failures to switch the affected operator to its verified fallback dataset.

A key precision mechanism is the \textbf{per-family deactivation} at step~5. Rather than comparing global offer counts — which would incorrectly block cleanup when the total scrape count differs from the database total due to unrelated family changes — the orchestrator groups the scraped offers by their source URL. Each URL corresponds to exactly one plan family (for example, one page for LEGEND, one for CAMPUCE, one for DjezzyNet). For each family that returned at least one offer in the current run, any database record sharing that source URL but absent from the current scrape is marked inactive. This detects removed plans precisely at the family level, independently of what other families returned in the same run.

\subsection{Normalisation, Validation, and Scheduled Automation}

Each operator presents plan data in a different format, so a normalisation pipeline applies the following transformations before any record is stored: data volumes in megabytes are converted to gigabytes; plan names are trimmed and stripped of promotional suffixes; missing voice or SMS values default to zero; unlimited values are stored as the sentinel \texttt{-1}; the plan type (prepaid, postpaid, data-only) is inferred from page context when not explicit; and a unique slug is generated from the normalised name. The pipeline outputs objects conforming to the \texttt{Offer} schema. The scrapers are accompanied by a snapshot-based test suite under \texttt{src/lib/scraper/\_\_tests\_\_} --- one parser-level test per operator (Djezzy CAMPUCE, Djezzy LEGEND, Ooredoo~500, Ooredoo~POP, Mobilis Pass Internet) verifies that the parser still extracts at least one offer from a frozen HTML fixture and that every extracted offer passes basic plausibility checks (no zero prices, no unrealistic data values, no \guillemotleft{}data == price\guillemotright{} parsing bugs) --- complemented by thirty independent tests covering multilingual unit parsing in \texttt{validate.ts}. This infrastructure has caught real parser regressions, most notably an Ooredoo POP page change in which data and price values briefly appeared in the same DOM node. The orchestrator runs automatically on a scheduled basis through the Next.js instrumentation hook (administrators may also trigger a manual run from the dashboard); after each successful run it inspects every updated offer and dispatches notifications: \texttt{price\_drop} to users who saved an offer whose price decreased, \texttt{new\_offer} to every registered user when a brand-new plan is inserted, and \texttt{scrape\_complete} or \texttt{scrape\_failed} to administrators only.

\subsection{Cross-Operator Comparison Routing}

One non-trivial design decision in the offers route concerns the comparison feature. When a user selects plans from different operators and navigates to the comparison page, the IDs are passed as a query parameter (\texttt{?ids=a,b,c}). The \texttt{/api/offers} handler detects this parameter and executes a direct lookup by ID list, deliberately bypassing the \texttt{isActive} filter that applies to the normal listing path. This ensures that saved plans remain comparable even if a subsequent scrape run has marked them inactive.

\subsection{Authentication}

User authentication is implemented with \textit{NextAuth.js} using the Credentials provider. Passwords are hashed with bcrypt at registration and verified at sign-in. Sessions are JWT-based with a thirty-day expiry. The \texttt{role} field (\texttt{USER} or \texttt{ADMIN}) is embedded in the session token and verified at the start of every admin-gated route handler. A one-time administrator-claim mechanism (\texttt{/api/admin/claim}) allows a registered user to elevate their role using a server-side secret defined in the \texttt{ADMIN\_CLAIM\_CODE} environment variable.

\section{Recommendation Engine}

\subsection{Two-Layer Decision Model}

The recommendation engine is implemented in \texttt{src/lib/recommendation.ts}. It separates the recommendation problem into two distinct layers: a categorical filtering layer that excludes offers incompatible with the user's hard constraints, and a tiered-ranking layer that orders the remaining offers according to the user's primary and secondary continuous priorities. The second layer is an applied form of \textbf{lexicographic preference ordering with bounded relaxation}, a well-established technique in multi-criteria decision making \parencite{Fishburn1974, Roberts1979}: the contribution of this work is the adaptation of that technique to a cold-start consumer-plan context, not the algorithm itself. The final defensible design (Figure~\ref{fig:rec-algo}) was reached after several rejected attempts (Section~3.4.4), each of which exposed a specific failure mode of the previous one.

\subsection{Hard Filters as Categorical Constraints}

The hard-filter layer treats the user's categorical preferences as binary go / no-go conditions rather than scoring contributions. Concretely, if the user has expressed a preferred operator (other than \guillemotleft{}any\guillemotright{}), only offers from that operator are kept; the same logic applies to plan type (prepaid / postpaid / data-only), network generation (4G / 5G), and the unlimited-calls and unlimited-SMS toggles. The budget acts as a price ceiling: offers above it are excluded entirely. This separation reflects the structural difference between continuous trade-offs (rankable) and categorical choices (filterable).

\subsection{Tiered Ranking with Explicit Priority Elicitation}

Rather than asking the user to assign numeric weights to each criterion — a known difficulty in multi-criteria decision contexts where users have well-defined preferences but cannot accurately quantify the corresponding weights \parencite{Roberts1979} — the engine asks the user to rank two criteria from the rankable set \{price, data\}. The first-ranked priority strictly determines an offer tier, and the second-ranked priority orders offers within that tier.

The merit of each rankable criterion is computed as a need-relative ratio, not as a pool-normalised score: this ensures that a catalogue outlier (for example, an absurdly cheap 10~DA plan with no data) cannot distort the ranking for users with a typical budget. The tier function \texttt{round($m_1 \times 4$) / 4} produces five discrete tier centres (0, 0.25, 0.5, 0.75, 1) covering the merit space in equal intervals of width $h = 0.25$. \textbf{Five centres rather than three or seven} was retained for two reasons: a smaller catalogue (~100 plans) does not statistically support finer-grained partitioning, and a larger number of tiers would shrink each tier toward a single offer, defeating the within-tier ordering purpose. \textbf{The secondary-merit multiplier of $0.24$} is set strictly below the tier width $h = 0.25$ to guarantee that no within-tier improvement on the secondary criterion can lift an offer past a higher tier; the small safety margin (0.24 < 0.25) absorbs floating-point rounding and keeps the boundary inviolate. The user's primary priority therefore strictly dominates the result, while the secondary priority still influences the final order.

\subsection{Iterative Design History}

The tiered model presented above was reached only after four earlier designs had been rejected. The first prototype added a flat $+12 / +8 / +4$ bonus to a hundred-point base fitness score for each ranked priority; the bonus was too small to overcome the base score, so the recommendations always followed price regardless of the user's choice. The second prototype replaced the bonus with a weighted sum of merits, with weights of 60\,\% on the primary and 40\,\% on the secondary; this allowed a great score on one criterion to compensate for a poor score on the other, contradicting the user's stated priority. The third prototype replaced the weighted sum with a weighted geometric mean of merits; tuning the weights merely shifted the symptom between \guillemotleft{}follows only price\guillemotright{} and \guillemotleft{}follows only data\guillemotright{} without ever producing a clean primary-then-secondary order. A fourth prototype attempted tiered ranking with a tier step of $0.1$, which made the cheapest tier so narrow that it contained only micro-plans, producing degenerate results. The final design (tier step $0.25$, with a multiplier of $0.24$ for the secondary) was retained: it reliably produces \guillemotleft{}follow the first priority, then get as close as possible to the second\guillemotright{}, which matches the user's stated mental model.

To illustrate the failure mode of the weighted geometric mean concretely, consider a user with budget 1\,400~DA, data need 20~GB, and priority ranking \texttt{[price, data]}. Two candidate offers are: $O_A$ at 200~DA / 3~GB and $O_B$ at 1\,400~DA / 25~GB. The need-relative merits are $m_{\mathrm{price}}(O_A) = 200/1400 \approx 0.14$, $m_{\mathrm{data}}(O_A) = 3/20 = 0.15$; $m_{\mathrm{price}}(O_B) = 1400/1400 = 1.00$, $m_{\mathrm{data}}(O_B) = 25/20 \to 1.00$ (clamped). With weights $(0.6, 0.4)$ and the geometric-mean composite $m_1^{0.6} \cdot m_2^{0.4}$, the model returns $0.143$ for $O_A$ and $1.000$ for $O_B$, ranking $O_B$ first --- precisely contradicting the user's stated primary preference for the price criterion, which would prefer $O_A$ since it sits closest to the lower-price end. The tiered model places $O_A$ in tier $0.00$ and $O_B$ in tier $1.00$; because the user's primary priority is price (lower merit is better in the engine's internal direction), tier $0.00$ leads strictly and $O_A$ is ranked first. The two models produce opposite top results from the same inputs --- which is the symptom the iterative process was eliminating.

The engine is called from two distinct contexts: the \texttt{/api/recommendations} route handler executes the algorithm synchronously in response to an explicit user request from the recommendations page (rate-limited at sixty requests per minute per IP), and the scraper orchestrator runs it in batch after each successful scrape cycle to dispatch personalised \texttt{recommendation} notifications when a user's top match has changed. The engine covers the case where the user has filled out a profile and wants the system to choose for them; the complementary case --- the user has a query in mind and wants the catalogue filtered by it --- is handled by the structured search interface described next.

Eight token kinds are recognised; Table~\ref{tab:search-tokens} lists each token with its example input and resulting filter.

Two assistance elements are visible on the offers page: \textbf{example chips} above the input (clickable presets such as \guillemotleft{}5 Go Djezzy\guillemotright{} or \guillemotleft{}Illimité 1000 DA\guillemotright{}), shown only when the input is empty, and a \textbf{\guillemotleft{}?\guillemotright{} help popover} next to the input which opens a syntax cheat-sheet listing every recognisable token kind with an example.

\section{Comparative Visualisation and Savings Calculator}

Two short user-facing features sit on top of the same recommendation backbone introduced above.

\paragraph{Comparative bar charts.} The comparison page renders, in addition to the side-by-side specification table, two per-metric bar charts comparing the selected plans on price (lower is better) and data volume (higher is better, with the sentinel value $-1$ shown as \guillemotleft{}$\infty$\guillemotright{}). Each plan's bar is coloured according to its operator using the palette defined in \texttt{src/lib/utils.ts}, and the corresponding columns of the table are tinted to match. The charts use the \texttt{recharts} library and are rendered client-side.

\paragraph{Savings calculator.} A dedicated page (\texttt{/savings}) implements the FICHE deliverable \guillemotleft{}calculateur d'économies potentielles\guillemotright{}. The user enters four values: the current monthly bill (continuous slider), the data need (continuous slider in GB), and two binary preferences for calls and SMS expressed as Any / Unlimited toggle pills --- the same control used on the \texttt{/recommend} page, to keep the input model coherent with the rest of the application and with the binary representation of calls and SMS in the database. The page calls the existing recommendations endpoint with the current bill as the budget; the result card displays the best-matching offer together with the monthly saving, the annual saving ($\times$~12), and the percentage reduction. When the current bill is already cheaper than every catalogue offer the page shows an \guillemotleft{}already optimal\guillemotright{} state instead of negative savings.

\end{table}

The two-stream separation is enforced at the source: every notification-dispatch function in the scraper orchestrator (\texttt{notifyUsers}, \texttt{notifyAdmins}, \texttt{notifyAdminsFailure}) filters the recipient set by the \texttt{User.role} field before writing any row. Each notification type also drives the click-through routing applied by the navbar bell and the admin panel: user-stream notifications navigate to the offer detail page or to \texttt{/recommend} depending on the type, while administrator-stream notifications navigate to \texttt{/admin?tab=history}.

The separation was introduced specifically to fix two defects in an earlier single-stream design. Without role filters on the dispatch functions, an administrator's feed was systematically polluted with consumer-facing alerts produced for every newly scraped offer. More damagingly, both administrator \guillemotleft{}scrape complete\guillemotright{} and user \guillemotleft{}new offer\guillemotright{} events used the same \texttt{type} value, so a non-administrator user clicking on a \guillemotleft{}new offer\guillemotright{} notification was routed to \texttt{/admin?tab=history} — a page they were not permitted to access. The current two-stream design — role-filtered dispatch, distinct \texttt{type} values, and type-aware routing — eliminates both defects by construction.

\section{Deployment}

{\sloppy The application is built for production with \texttt{next build}, which performs static analysis, tree-shaking, and route-level code splitting. The resulting artefact is a Node.js server launched with \texttt{next start}. Three environment variables must be set: \texttt{DATABASE\_URL} (path to the SQLite file), \texttt{NEXTAUTH\_SECRET} (JWT signing key), and \texttt{NEXTAUTH\_URL} (base URL). The SQLite file is the only persistent artefact that must be preserved across deployments. The current evaluation deployment runs in production mode on a single machine; public deployment to a managed cloud host is identified as a perspective in the general conclusion.\par}
